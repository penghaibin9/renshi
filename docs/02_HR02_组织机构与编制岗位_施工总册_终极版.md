# 0. 结论先行

HR02 绝不是“把 Horilla 的 Company / Department / JobPosition 换成中文并做一棵组织树”。

它是整个人事系统中最重要的**结构事实与岗位控制域（Workforce Structure & Position Control Domain）**，必须回答六个问题：

1. **学校现在有哪些正式组织，历史上又是什么样？** —— HR02-01 组织机构
2. **行政、党组织、教学和业务关系如何对应？** —— HR02-02 党政组织与业务关系
3. **学校和各单位到底核定多少人、多少职数、什么结构？** —— HR02-03 编制方案
4. **学校允许设置什么类别、什么等级、什么职责的岗位？** —— HR02-04 岗位目录
5. **每个单位实际允许占用哪些岗位、已占多少、缺多少、是否超限？** —— HR02-05 岗位编制台账
6. **机构撤并、改名、拆分、岗位迁移后，过去的人事事实能不能保持正确？** —— HR02-06 组织岗位历史

HR02 必须贯彻一句总原则：

> **组织是组织，编制是编制，岗位目录是岗位标准，岗位实例/岗位额度是岗位供给，人是谁以及谁占了什么岗位是 HR03 的任职事实。任何一层都不能偷懒合并。**

顶级实现应满足：

> **稳定身份 → 生效期版本 → 组织多维关系 → 编制/职数控制 → 岗位目录 → 具体岗位供给 → 任职占用 → 历史可回看 → 变更有审批 → 全链路租户与数据范围隔离。**

因此本模块禁止以下低质量实现：

- 把 `Department` 直接加 `parent_id` 就宣布“组织架构完成”；
- 把 `Company` 同时当 SaaS 租户、学校、学院、法人和组织节点；
- 把当前员工人数反推“核定编制”；
- 把当前员工岗位字段当作“岗位设置方案”；
- 把职称（教授/副教授）等同于岗位等级；
- 把行政职务等同于岗位目录；
- 把“岗位目录”和“岗位席位/岗位额度”混为一张表；
- 机构改名直接 UPDATE，导致三年前记录也显示新名字；
- 机构撤并直接 DELETE；
- 机构调整时自动、静默地把人员历史全改到新单位；
- 允许跨学校父子组织、跨学校岗位挂接；
- 允许组织树出现环；
- 允许同一个正式版本存在重叠生效区间；
- 把上海/某校公开的结构比例写死成全国统一比例；
- 把 Horilla `JobRole` 强行解释为中国高校岗位等级；
- 在 HR02 里直接修改 HR03 人员任职事实；
- 历史日期视图仍允许编辑当前数据；
- 未来生效的机构调整没有预览和影响分析；
- Excel 导入遇到一条错就产生半成功数据；
- 用浏览器数组计算编制余额、空岗、超编；
- 组织树一次性加载全校所有人员明细；
- 为了“图好看”制造无法解释的 3D 组织图、渐变大屏和无意义动画。

# 1. 施工前提与依赖

## 1.1 H0 基线硬门

HR02 开始正式写权威模型前必须确认：

- Docker 可重复构建；
- PostgreSQL 迁移可正常执行；
- Django system check 通过；
- `/health/`、`/ready/` 可作为运行态闸门；
- GitHub CI 可以真实执行迁移和测试；
- Horilla 原始上游测试欠账已经单独标识，不能和跃科新增回归混淆；
- PostgreSQL 版本、扩展能力和迁移权限已确认。

HR02 如果采用 PostgreSQL `ExclusionConstraint` / `btree_gist` 做有效期不重叠约束，必须在 HR02-S0 做数据库能力预检；若生产环境无法启用扩展，则必须使用事务级锁 + 唯一活动版本约束 + 并发测试实现等价保护，不能只靠前端校验。

## 1.2 A0 多学校隔离硬门

HR02 是最容易造成“大面积跨学校污染”的模块之一，因此 A0 必须先满足：

- `Company` 已被明确升级为学校租户安全边界；
- tenant/school 由服务端可信上下文解析，不信任前端随意传值；
- 无 school context 默认 fail-closed；
- 用户只能选择有 membership 的学校；
- 所有 HR02 权威表必须含 `tenant_id` 或通过不可绕过的 tenant relation 归属；
- 任意 FK 必须验证目标对象属于同一 tenant；
- 组织树、岗位树、Excel、导出、历史查询、搜索、自动补全都必须套同一 scope；
- 后台任务必须显式绑定 tenant；
- `.objects.all()`、管理命令、异步任务不得默认跨租户；
- 跨学校共享模板只能通过显式 `system_scope` + 平台级配置表实现，不允许 `tenant_id=NULL` 默认共享正式人事数据。

## 1.3 HR01 依赖关系

HR01 可以先使用 `LEGACY_CURRENT_SNAPSHOT`，但 HR02 一旦权威化：

- 人事总览中的学院分布必须切到 HR02 组织事实；
- 编制、空岗、超编、岗位结构风险必须由 HR02 Provider 提供；
- `DUAL_READ_COMPARE` 完成后，HR01 不得继续从 Horilla `Department/JobPosition` 取权威口径。

## 1.4 HR03 边界

HR02 不存“这个人现在属于哪个学院”的最终人事任职真相。

HR02 只定义：

- 组织；
- 组织之间的关系；
- 编制/职数；
- 岗位目录；
- 岗位供给/岗位实例；
- 组织与岗位变更历史。

HR03 定义：

- 教职工是谁；
- 某人何时属于哪个组织；
- 某人何时占用哪个岗位；
- 主岗/兼岗；
- 人员任职历史。

因此：

> **HR02 机构撤并只能生成“人员任职影响清单/待迁移任务”，不能直接静默 UPDATE HR03 历史。**

## 1.5 HR14 边界

HR02 定义“岗位存在与可占用多少”；HR14 定义“某轮岗位聘任中谁申请、谁评审、谁被正式聘到什么等级”。

不要在 HR02 做岗位竞聘、聘任评审、聘期考核。

# 2. 三家顶级成熟 HCM 对标结论

本总册吸收 Workday、SAP SuccessFactors、Oracle Fusion HCM 在组织与岗位管理上的成熟思想，但不复制其界面、代码或受保护资产。

## 2.1 Workday：Supervisory Organization + Position Management

可吸收的核心思想：

- 组织层级是独立的管理结构；
- Position Management 与 Job Management 是不同 staffing model；
- Position Management 强调“先有批准的岗位，再允许招人/调动/晋升”；
- 单个 position 可以有独立招聘限制；
- 可以报告 open/filled positions；
- position 独立于 incumbent，人离开后岗位仍然存在；
- 支持 position history；
- position 可以随组织重组移动；
- 组织结构与 staffing strategy 必须一起设计；
- 不同组织可以采用不同控制强度。

### 转化为跃科 HR02

跃科不照搬 Workday 两套 staffing model 的产品术语，但吸收“**控制模式可差异化**”这一思想：

```text
POSITION_CONTROL
    对管理岗、领导职数、特设岗、稀缺岗位逐岗位控制

POOL_CONTROL
    对批量教师岗位或学校政策允许的类别按“机构+岗位类别+等级+额度”控制
```

V1 数据模型必须支持两种方式，但默认高校事业单位正式岗位优先采用 `POSITION_CONTROL`；只有明确业务需要时才使用 `POOL_CONTROL`。

这样既能满足高校严格岗位控制，又避免把几千个完全同质岗位都做成难维护的手工座位。

---

## 2.2 SAP SuccessFactors：Position as Leading Hierarchy

可吸收的核心思想：

- position 可以独立于员工存在；
- position 有当前 incumbent、历史 incumbent、FTE、To Be Hired 状态；
- Position Org Chart 同时展示岗位与人员；
- 支持创建、更新、停用 position；
- 支持查看过去、现在和未来的 position；
- position 可以驱动招聘和入职默认值；
- position 与 job information 有受控同步；
- Company Structure Overview 把组织对象和 position 关系统一可视化；
- Role-Based Permission 控制谁能看/改过去、现在、未来岗位。

### 转化为跃科 HR02

- 岗位必须有 stable ID；
- 人员不是岗位的一部分；
- 当前占用只通过 HR03 assignment 投影；
- 支持未来生效岗位；
- 支持历史 as-of 查看；
- 支持空岗、部分占用、冻结、关闭；
- 岗位变化自动向 HR04 招聘、HR03 任职、HR14 聘任提供事件，而不是相互直接改表；
- 岗位组织图可作为辅助视图，但不能成为唯一操作入口。

---

## 2.3 Oracle Fusion HCM：Workforce Structures

可吸收的核心思想：

Oracle 将以下对象明确拆开：

- Department；
- Division；
- Organization Tree；
- Department Tree；
- Position Tree；
- Location；
- Job；
- Position；
- Grade；
- Grade Rate；
- Grade Ladder。

核心启发：

> **岗位名称、岗位实例、组织、等级是不同维度，不能为了省表合并成一个字段。**

### 转化为跃科 HR02

跃科 V1 冻结为：

```text
Tenant / School
  ↓
HrOrganization
  ↓
HrStaffingPlan / Quota
  ↓
HrPostCatalog
  ↓
HrPosition
  ↓
HR03 StaffAssignment
```

专业技术职称留在 HR03/HR13，岗位聘任结果留在 HR14；HR02 只维护岗位等级“允许设置什么、目前有哪些岗位”。

## 2.4 三家共同精华：HR02 十条产品原则

1. **组织身份稳定，属性可以随时间变化**；
2. **岗位独立于人员**；
3. **岗位标准与岗位实例分离**；
4. **空岗也是正式业务对象**；
5. **过去/现在/未来都可以查看**；
6. **组织重组和岗位移动是正式业务事件**；
7. **岗位控制必须和审批、额度约束关联**；
8. **岗位/组织变化可以驱动招聘与任职，但不能跨域私写**；
9. **Role/Data Scope 控制分析与操作**；
10. **数据模型必须支持“重组后历史不漂移”**。

# 3. 中国高校业务校正

中国高校尤其是事业单位/高职的人事结构，比普通企业多出三个关键维度：

1. **编制与岗位总量控制**；
2. **管理、专业技术、工勤三类岗位及等级结构**；
3. **行政、党组织、教学等多组织关系并存**。

高职公开人事系统需求已经明确提出：

- 党政组织树双维度；
- 业务匹配映射；
- 组织机构与岗位管理；
- 多角色教职工全周期管理；
- 校院两级贯通。

高校岗位管理政策普遍强调：

- 科学设岗、宏观调控；
- 按岗聘用；
- 岗位总量；
- 结构比例；
- 管理岗位、专业技术岗位、工勤技能岗位；
- 专业技术岗位内部等级；
- 特设岗位；
- 岗位设置方案和聘用结果备案。

因此跃科 HR02 绝对不能写死“某省比例”或“某校比例”。正确做法是：

> **建立可版本化的高校岗位结构规则模型，并提供政策模板，但每所学校的正式比例、等级、控制阈值都由本校审批后的方案决定。**

# 4. Horilla 2.0 现状审计与接管判断

## 4.1 当前可利用对象

Horilla 当前已有：

```text
base.Company
base.Department
base.JobPosition
base.JobRole
employee.Employee
employee.EmployeeWorkInformation
HorillaCompanyManager
permission / group
history / audit
forms / filters / CBV list
employee organization chart 入口
```

其中：

- `Company` 有名称、地址、地区、图标等；
- `Department` 通过 M2M 关联 Company；
- `JobPosition` 通过 FK 关联 Department，并可关联 Company；
- `JobRole` 依附 JobPosition；
- `EmployeeWorkInformation` 当前直接保存 department、job_position、job_role、company、employee_type 等当前值。

## 4.2 Horilla 当前模型的本质问题

### P0-01：Company 语义混乱

Horilla 原设计中 Company 是企业单位维度，并不等于我们需要的“不可跨越的学校租户安全边界 + 学校组织事实”。

A0 应保留 `Company` 作为 tenant identity/security boundary；HR02 不再用它表示学院/部门。

### P0-02：Department 不是历史事实模型

当前 Department：

- 没有 parent hierarchy；
- 没有 effective_from/effective_to；
- 没有撤并/拆分语义；
- 没有组织维度；
- 允许 M2M company；
- 没有正式 change case；
- 不能还原历史组织树。

### P0-03：JobPosition 不能代表高校岗位体系

当前 `JobPosition`：

- 依附当前 Department；
- 没有岗位类别；
- 没有岗位等级；
- 没有核定数；
- 没有 FTE/capacity；
- 没有 open/filled/frozen 生命周期；
- 没有 future effective；
- 没有 position history；
- 无法区分“岗位标准”和“具体岗位”。

### P0-04：JobRole 不能自动解释为高校岗位等级

Horilla `JobRole` 只是 JobPosition 下的角色字段，不能无证据映射成：

- 教授一级/二级；
- 管理七级/八级；
- 工勤等级；
- 行政职务。

Legacy migration 必须默认 `COMPAT_ONLY`，除非学校明确提供映射规则。

### P0-05：EmployeeWorkInformation 把当前事实直接固化

当前员工表直接存：

```text
department
job_position
job_role
company
employee_type
date_joining
contract_end_date
...
```

它适合作为 Horilla 现有模块的**当前投影**，不适合作为 HR02/HR03 长期权威源。

### P0-06：无正式“编制”概念

Horilla 没有权威的：

- 编制方案；
- 核定人数；
- 岗位总量；
- 领导职数；
- 岗位等级结构比例；
- 超编/缺编控制。

所以禁止把 `Employee.objects.count()` 当核定编制。

## 4.3 接管总策略

| Horilla 对象 | HR02 决策 | 终局用途 |
|---|---|---|
| `Company` | ADAPT | A0 学校租户安全边界；保留 stable tenant id |
| `Department` | COMPAT_ONLY | 由 HR02 当前行政组织投影生成，旧模块兼容 |
| `JobPosition` | COMPAT_ONLY | 由 HR02 当前岗位投影生成，旧模块兼容 |
| `JobRole` | COMPAT_ONLY / DEFER | 不自动映射岗位等级 |
| `EmployeeWorkInformation.department` | PROJECT | HR03 上线前 current snapshot；之后由权威任职投影 |
| `EmployeeWorkInformation.job_position` | PROJECT | 同上 |
| `HorillaCompanyManager` | REWRITE/HARDEN | A0 fail-closed tenant scope |
| 旧组织图 UI | ADAPT | 交互思路可参考，数据源改 HR02 |
| 旧表格/筛选/分页组件 | ADAPT | 公共 UI 可复用 |
| 旧 Department/JobPosition 写入口 | REMOVE_AFTER_CUTOVER | Authority 切换后隐藏/只读 |

# 5. HR02 信息架构冻结

HR02 只保留以下 6 个三级模块，不继续横向加菜单：

## HR02-01 组织机构

解决：

- 正式组织树；
- 学校/学院/系部/科室/直属单位/虚拟单位；
- 组织代码、类型、负责人；
- 当前/历史/未来结构；
- 新建、改名、迁移、停用等正式变更入口。

## HR02-02 党政组织与业务关系

解决：

- 行政组织；
- 党组织；
- 教学组织；
- 业务/归口关系；
- 多树映射；
- 一对一/一对多关系；
- 关系历史。

## HR02-03 编制方案

解决：

- 年度/周期编制方案；
- 学校总量；
- 学院/单位分配；
- 编制来源；
- 岗位总量；
- 领导职数；
- 结构比例；
- 调整、审批、冻结、版本。

## HR02-04 岗位目录

解决：

- 管理岗位；
- 专业技术岗位；
- 教师岗位；
- 其他专技岗位；
- 工勤技能岗位；
- 特设岗位；
- 岗位等级；
- 职责；
- 任职条件；
- 标准工时/FTE；
- 控制模式。

## HR02-05 岗位编制台账

解决：

- 各单位实际岗位供给；
- 核定岗位；
- 空岗；
- 已占用；
- 部分占用；
- 冻结；
- 超岗；
- 结构比例；
- position/control pool；
- 与 HR03 占岗事实的实时对账。

## HR02-06 组织岗位历史

解决：

- 改名；
- 上下级调整；
- 合并；
- 拆分；
- 撤销；

## 6.1 核心角色

# 7. HR02 核心领域模型：五层真相

## 7.1 第一层：Tenant / School

继续使用 A0 的 `Company` 作为学校租户身份。

重要裁决：

> `Company.id` 是安全边界，不是高校组织树里的可随意撤并节点。

每个 tenant 必须有且只有一个 HR02 根组织：

```text
HrOrganization(org_type=SCHOOL)
```

`Company` 名称可接受 HR02 根组织当前名称的兼容投影，但 tenant id 永远不因改名变化。

## 7.2 第二层：Organization

表示学校、学院、系部、科室、直属单位、党组织、教学组织等稳定组织身份。

## 7.3 第三层：Staffing Plan / Quota

表示学校批准的：

- 人员总量；
- 编制来源；
- 单位分配；
- 岗位总量；
- 领导职数；
- 岗位类别/等级结构规则。

**实际人数不是编制。**

## 7.4 第四层：Post Catalog

岗位“标准/目录”，回答：

> 这个岗位是什么工作、属于哪类、什么等级、要求什么条件？

## 7.5 第五层：Position / Position Pool

回答：

> 某单位实际被批准拥有多少这样的岗位，目前能不能占、还剩多少？

人员占用由 HR03 提供。

# 8. 稳定身份与生效期版本设计

HR02 必须贯彻：

> **Stable Identity + Effective-Dated Version**

不能把所有东西做成一条永远 UPDATE 的行。

## 8.1 `HrOrganization`

稳定身份建议：

```text
id UUID / bigint
public_id
 tenant_id
stable_code
org_dimension
created_at
created_by
closed_at
```

`stable_code` 原则：

- tenant 内唯一；
- 一经正式生效，默认不可重用；
- 如学校确需修改显示编码，用 alias/history，不复用旧编码指向新实体。

## 8.2 `HrOrganizationVersion`

```text
id
organization_id
tenant_id
name
short_name
org_type
parent_organization_id
status
leader_position_id?  # 仅引用岗位，不直接引用员工
location_id?
display_order
validity  # PostgreSQL daterange, [from,to)
change_case_id
source
version_no
created_at
created_by
```

不建议把负责人直接永久存在组织主表。负责人是任职关系，最终应由 HR03 / HR14 投影；HR02 可以展示当前负责人，但不成为权威人事实体。

## 8.3 有效期约束

同一 `organization_id`：

- 正式有效版本区间不得重叠；
- 一个日期最多解析出一个有效版本；
- 未来 approved version 可以存在；
- DRAFT 不参与正式 as-of 查询；
- REJECTED/CANCELLED 永不进入正式版本。

推荐 PostgreSQL：

```text
EXCLUDE USING GIST (
  organization_id WITH =,
  validity WITH &&
)
WHERE (status IN ('APPROVED','EFFECTIVE','SUPERSEDED'))
```

实现时根据最终状态设计精确调整。

## 8.4 历史视图原则

```text
asOf = today
    当前视图，可写

asOf < today
    历史只读，显示“历史日期”提示条

asOf > today
    未来预览，只读；仅允许进入对应变更 Case 编辑，而不是直接改未来树
```

## 11.9 方案校验

- 总分配是否超过学校总量；
- 组织是否有效；
- 组织是否当前/未来存在；
- 岗位类别是否合法；
- 结构比例是否超阈值；
- 领导职数是否超限；
- 是否存在负数；
- 是否存在与未来组织撤并冲突；
- 当前已占人数是否大于新核定且缺少过渡说明；
- 是否存在 plan line 重复；
- 生效时间是否与上一方案重叠。

## 13.4 为什么需要两种控制模式

- 校领导/院领导岗位；

- 特设岗位；

- 大量相同基础岗位；
- 不要求逐座位编号的用工额度。

## 14.5 组织合并

必须明确：

```text
A + B → C
```

不允许简单：

```text
UPDATE staff SET department=C WHERE department IN (A,B)
DELETE A,B
```

正确流程：

1. 创建/指定目标组织 C；
2. 确定 A/B 关闭日期；
3. 生成下级组织迁移方案；
4. 生成岗位迁移方案；
5. 生成 HR03 人员任职影响清单；
6. 生成 scope/permission 影响；
7. 生成下游业务引用影响；
8. 人工确认；
9. 审批；
10. 到生效日产生新组织版本/关系；
11. HR03 通过正式变更事件处理人员未来任职；
12. A/B 历史仍存在。

## 14.6 组织拆分

同样不能猜：

```text
A → B + C
```

必须要求明确：

- 子组织归属；
- 岗位归属；
- 编制分配；
- 人员迁移规则/名单；
- 权限重算；
- 未决业务归属。

## 14.7 改名

组织改名：

- stable org id 不变；
- 新建 future/effective version；
- 历史日期仍显示旧名；
- 搜索可通过旧名 alias 找到同一 org；
- 导出历史报表根据 as-of 输出历史名。

# 20. 关键领域不变量（必须写成测试）

## INV-01 Tenant

任何 Organization/Relation/Plan/Post/Position FK 都不能跨 tenant。

## INV-02 Root

每 tenant 恰好一个当前 SCHOOL 根组织。

## INV-03 No Cycle

任何 primary hierarchy 不得出现环。

## INV-04 Effective Overlap

同一 stable entity 的正式版本有效期不得重叠。

## INV-05 Historical Immutable

已过期正式版本不得普通 PATCH。

## INV-06 Code No Reuse

正式使用过的 stable code 不得被另一个实体重新占用。

## INV-07 Quota != Occupancy

核定编制/岗位额度不得由当前人数自动回填。

## INV-08 Position != Person

Position 生命周期不由 incumbent 生命周期决定。

## INV-09 Occupancy Derived

岗位占用由 HR03 assignment 派生，不允许 HR02 手填“已占用”。

## INV-10 Reorg No Silent Staff Rewrite

组织重组不能直接篡改 HR03 历史。

## INV-11 Current Projection Not Authority

Horilla Department/JobPosition/EmployeeWorkInformation 只能是兼容投影。

## INV-12 Historical View Readonly

`asOf < today` 的所有写 API/UI 必须拒绝。

## INV-13 Approved Future Change Protected

批准后的 future version 不能直接修改，必须走变更/撤销流程。

## INV-14 Quota Control

HARD control 下，不得创建导致正式额度超限的 position/assignment reservation。

## INV-15 Ratio Rules Versioned

结构比例规则必须关联方案版本，不能“今天改阈值导致去年违规”。

# 30. Legacy 退出合同

HR02 同样采用三阶段：

```text
LEGACY_STRUCTURE_ONLY
        ↓
DUAL_READ_COMPARE
        ↓
HR02_AUTHORITY
```

## 30.1 LEGACY_STRUCTURE_ONLY

- Horilla Department/JobPosition 仍为旧模块当前结构；
- HR02 新模型可以建立但不对旧模块强切；
- 所有 HR02 页面明确 dataBasis。

## 30.2 DUAL_READ_COMPARE

比较：

- 当前部门数；
- 当前组织映射；
- 员工 current department mapping；
- current job position mapping；
- tenant 边界；
- 空映射/一对多异常。

生成 reconcile report。

## 30.3 HR02_AUTHORITY

进入后：

- 新增/改组织只写 HR02；
- Department/JobPosition 由 projection service 维护；
- legacy 表单关闭；
- legacy write API 返回 `HR02_LEGACY_WRITE_DISABLED`；
- HR02 projection 故障不得自动改回“人工写 legacy”；
- 生产 code path 不允许 fallback 以 legacy 覆盖新事实。

## 30.4 Cutover 硬门

必须满足：

- tenant mapping 100%；
- active Department 映射 100% 或有明确豁免；
- active Employee current org mapping 100% 或有阻断清单；
- current JobPosition mapping 100% 或明确弃用；
- 无跨 tenant mapping；
- 组织树无 cycle；
- current as-of tree 可完整读取；
- legacy projection 回归全绿；
- HR01 provider 可切新源。

# 49. 终极补强：遗漏修正与前 1% 设计约束

## 50.1 岗位预占：`HrPositionReservation`

### 为什么必须有

典型并发事故：

```text
某学院只剩 1 个教师岗位

招聘流程 A 10:00 查询：可用 1
招聘流程 B 10:00 查询：可用 1
A 创建招聘
B 创建招聘
两边最终各录用 1 人
→ 额度超卖
```

只做 `availability GET` 解决不了并发。

因此 HR02 必须向 HR04 招聘、HR06 调动、HR05 入职、HR14 聘任等域提供**受控岗位预占**。

### 模型

```text
HrPositionReservation
- id
- tenant_id
- reservation_no
- position_id? / position_pool_id?
- source_domain
- source_business_type
- source_business_id
- reserved_count
- reserved_fte
- status
- reserved_at
- expires_at
- committed_at
- released_at
- idempotency_key
- version
```

状态：

```text
HELD
COMMITTED
RELEASED
EXPIRED
CANCELLED
```

### 规则

- HARD control 的 availability 计算必须扣除有效 `HELD` reservation；
- reservation 创建必须事务锁定 position/pool；
- 同一业务幂等重试不得重复占额；
- 招聘取消/录用失败必须 release；
- 超时 reservation 自动 expire；
- 最终 HR03 assignment 生效时使用 `commit reservation`，而不是重新盲查一次；
- reservation 不等于人员正式任职；
- 所有 reservation 变更写审计。

### API

```http
POST /api/hr/v1/structure/position-reservations
POST /api/hr/v1/structure/position-reservations/{id}/commit
POST /api/hr/v1/structure/position-reservations/{id}/release
GET  /api/hr/v1/structure/position-reservations?sourceBusinessId=...
```

### 并发测试

至少 20 个并发请求争抢 1 个 position：

```text
成功 HELD = 1
其余 = HR02_POSITION_NOT_AVAILABLE
最终 occupied/reserved 不超额
```

```text
POS-{ORGCODE}-{YEAR}-{SEQ}
```

但规则变更不得修改历史 position code。

### External Identifier

另建映射，不要把不同系统编码塞进一个字段：

```text
HrExternalIdentifier
- tenant
- entity_type
- entity_id
- system_code
- external_id
- validity
```

支持：

- 数字校园；
- 财务；
- 一卡通；
- 上级报表；
- 数据中台。

---

## 50.3 Campus / Location 与 Organization 必须分离

“校区”有时是组织，有时只是物理地点。

规则：

- 如果校区有独立管理/组织意义，可建立 `HrOrganization(org_type=CAMPUS)`；
- 物理办公地址、教学地点统一引用 Location 基础字典；
- 不把地址字符串当组织层级；
- 一个组织可以跨多个 location；
- 一个 location 可以服务多个组织。

禁止：

```text
parent = 长沙校区
```

仅仅因为员工办公地点在长沙校区，就推断它是组织父节点。

---

## 50.4 学校时区与正式生效时点

HR02 的 `effectiveDate` 必须按学校时区解释。

例如学校时区：

```text
Asia/Shanghai
```

则：

```text
2026-09-01
```

表示学校本地 2026-09-01 00:00 起新版本有效。

禁止使用 GitHub runner / Docker server UTC 日期直接决定“今天是否生效”。

必须测试：

- UTC 前一天 16:00 跨上海 00:00；
- 月末；
- 年末；
- leap day；
- future preview 到 effective 的边界。

---

## 50.5 高风险变更职责分离（SoD）

以下动作默认不得由同一普通用户“发起+最终批准”：

- 学校级组织 merge/split；
- 大规模编制下调；
- 领导职数调整；
- 正式岗位方案生效；
- 批量关闭有历史引用的岗位；
- authority cutover。

工作流可配置，但系统必须支持：

```text
initiator != final_approver
```

超级管理员 break-glass 例外必须：

- reason；
- 二次认证（如全局安全底座支持）；
- 强审计；
- 事后复核。

---

## 50.6 下游历史引用合同

下游正式业务对象推荐同时保存：

```text
organization_id         # stable reference
organization_snapshot   # 当时关键展示快照（必要时）
as_of/effective_at       # 事实时间
```

读取原则：

- “当前组织”场景 → current resolver；
- “历史业务”场景 → 按业务发生时间 as-of resolver；
- 法定/归档文书 → 可使用冻结 snapshot；
- 不允许只存组织名字；
- 不允许历史业务始终 join current version。

这条合同必须在 HR03、HR07、HR12、HR13、HR14 等后续总册重复引用。

## 50.7 组织停用依赖矩阵

任何组织 `DEACTIVATE` 前必须检查：

```text
active child organizations
future child versions
active positions
future positions
position reservations
current HR03 assignments
future HR03 assignments
open recruitment requisitions
open onboarding cases
open personnel changes
```

```text

```

用户必须在 Preview 中看到，不允许点一下“停用”直接成功。

## 50.8 Authority Feature Flag 必须 tenant 级

禁止一个全局：

```text
HR02_ENABLED=true
```

把所有学校同时切换。

至少支持：

```text
hr02AuthorityMode(tenant_id)
```

值：

```text
LEGACY_STRUCTURE_ONLY
DUAL_READ_COMPARE
HR02_AUTHORITY
```

这样：

- 学校 A 可先切；
- 学校 B 继续迁移；
- 问题隔离；
- 不需要全平台一次“大爆炸上线”。

切换必须写：

```text
operator
old_mode
new_mode
reason
reconcile_report_id
occurred_at
```

## 50.9 数据删除与保留

HR02 正式实体默认**不物理删除**。

允许 hard delete 的范围仅限：

- 从未提交、从未引用的 DRAFT；
- 自动化测试数据；
- 明确平台治理下的无效临时对象。

正式生效过：

```text
Organization
StaffingPlan
PostCatalog
Position
Relation
```

只能：

- close；
- supersede；
- deactivate；
- correct via controlled correction process。

数据库级 `CASCADE` 必须审计，不能因删除一个新对象连带清掉历史事实。

# 52. 最终终极验收补充

在第 48 节封板口令之外，再加 8 条一票否决：

1. **岗位无 reservation 并发保护 → NOT READY**；
2. **组织/岗位编码可以历史复用 → NOT READY**；
3. **effectiveDate 使用服务器 UTC 直接解释 → NOT READY**；
4. **高风险 reorg 可自己发起自己批准且无受控例外 → NOT READY**；
5. **组织停用不检查下游未决业务 → NOT READY**；
6. **authority flag 只能全平台切换 → NOT READY**；
7. **历史下游记录只 join current org name → NOT READY**；

只有全部通过，HR02 才真正具备生产级“组织机构与编制岗位”强度。
