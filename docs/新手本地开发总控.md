# Renshi 新手本地开发总控

## 你只需要记住三件事

1. 产品只有 HR01～HR18，不再另外创造“第19模块”。
2. 日常开发目录只有 `F:\高校人事系统\renshi-ui-v2`；旧 `renshi` 目录只作历史对照。
3. 一次只改一个模块、完成一个可验收的小任务，再提交。

## 每天固定六步

```text
1. 打开 Renshi-18模块.code-workspace
2. 到 modules/README.md 选择一个模块
3. 只写一个任务：例如“HR06 新建异动页能真实提交”
4. 修改该模块的模板、CSS、JS和必要后端
5. 跑模块测试 + 页面测试
6. 更新模块 README 的“当前任务”，再提交
```

开始前先检查：

```powershell
git status --short --branch
python scripts/check_hr18_structure.py
```

结束前至少检查：

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test <本次模块 app 名> --keepdb --noinput
```

## 前端重构规则

### 可以共享的只有这些

- 全局页面壳、导航、面包屑。
- `static/hr/css/hr-v2.css` 设计令牌和通用组件。
- API client、错误信封、loading/empty/error/unavailable 状态组件。

### 模块自己的文件最终放回模块 app

```text
hr_xxx/
  templates/hr_xxx/
  static/hr_xxx/css/
  static/hr_xxx/js/
  tests/
```

现有散落在根 `templates/hr/`、`static/hr/css/`、`static/hr/js/pages/` 的文件不要一次性移动。每重构一个模块时，只迁该模块文件；保留兼容入口，测试通过后再删旧入口。

### 一个页面完成的标准

- 使用真实 API，不写假 KPI、假人员、假成功状态。
- 有 loading、empty、error、unavailable 四种状态。
- tenant、permission、SELF 范围由后端判断。
- 桌面和手机页面都能操作。
- 至少有一个页面契约测试；关键流程有真实浏览器测试。
- 后端失败时页面不能显示“操作成功”。

## 推荐施工顺序

```text
第一阶段：HR01～HR08 主人事链页面统一
第二阶段：HR09～HR14 教师发展、评价、职称聘任
第三阶段：HR15～HR18 薪酬、离退、自助、数据中心
第四阶段：跨模块 E2E、真实数据迁移和上线验收
```

当前优先不要继续同时铺18个页面。先完成正在施工的 HR06，然后逐个模块收口。

## Git 使用底线

- 不在旧 `renshi/main` 目录继续开发。
- 不使用 `git add .`；只提交本模块确认过的文件。
- 一个提交只解决一个模块的一件事。
- 本地测试绿不等于可上线；合并前仍要看 MySQL、浏览器和 Docker 门禁。

## 目录为什么不直接大搬家

`hr_control_center`、`hr_staff` 等名称已经写入 Django app、Python import、migration、URL、测试和数据库迁移历史。直接改成 `HR01` 会造成大面积断裂。`modules/` 和 18模块 workspace 先把人的视角归拢成18个入口；底层技术目录在逐模块重构时再安全收敛。
