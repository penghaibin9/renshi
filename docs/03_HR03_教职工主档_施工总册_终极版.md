# 0. 结论先行

HR03 不是“重做一个 Employee CRUD 页面”，也不是“把 Horilla 员工详情页翻译成中文”。

HR03 是整个人事系统真正的**人员身份与历史事实核心（Person & Workforce Fact Core）**。它必须解决六个根本问题：

1. **学校到底有哪些教职工，每个人唯一是谁？** —— HR03-01 教职工名册；
2. **一个人的当前权威人事状态是什么，管理员一眼能否看清？** —— HR03-02 教职工主档；
3. **这个人在任何历史时间点属于哪个单位、占什么岗位、是什么身份？** —— HR03-03 任职与身份履历；
4. **他的教育、工作、资格、证书和人才荣誉事实是什么？** —— HR03-04 教育资格履历；
5. **支撑上述事实的原件、证明、审批文件和版本证据在哪里？** —— HR03-05 人事材料档案；
6. **发现信息错误时，如何更正而不破坏过去已经发生的业务事实？** —— HR03-06 信息更正与历史。

HR03 必须贯彻一句总原则：

> **自然人是自然人，教职工身份是教职工身份，聘用关系是聘用关系，任职/岗位是时态事实，账号只是访问凭证，材料是证据；任何一层都不能再被一个 `Employee` 当前状态表吞掉。**

最终权威模型必须能够表达：

```text
Person
  ├─ PersonIdentity / Contact / SensitiveIdentity
  ├─ StaffMaster（某学校下的教职工身份）
  │    ├─ EmploymentRelationship ①
  │    │    ├─ Assignment A（主岗）
  │    │    ├─ Assignment B（兼岗）
  │    │    └─ StatusHistory
  │    ├─ EmploymentRelationship ②（返聘/再次入职/外聘等）
  │    ├─ EducationExperience[]
  │    ├─ WorkExperience[]
  │    ├─ Qualification/Certificate[]
  │    ├─ TalentHonor[]
  │    ├─ StaffMaterial[]
  │    └─ CorrectionCase[]
  └─ Account / SSO Mapping（独立关系，不是 Person 本体）
```

顶级实现必须回答“现在是什么”和“当时是什么”两个问题：

```text
查询 as_of = 今天
→ 返回当前学院、主岗、身份、状态、职称投影等

查询 as_of = 2024-10-01
→ 返回 2024-10-01 当时真实有效的组织、岗位、身份和关系
```

因此禁止以下低质量实现：

- 继续把 `Employee` 当未来所有人员事实的权威表；
- 把登录账号和教职工身份一一绑死；
- 一个自然人返聘/再次入职就创建第二个“人”；
- 一个人兼任多个组织/岗位时仍只保存一个 `department_id/job_position_id`；
- 调学院时直接 UPDATE 当前部门，不留 effective-dated 历史；
- 用 `is_active` 代替完整在职/离职/退休/待入职等人事状态；
- 用 email 当自然人唯一标识；
- 依赖身份证明文做所有去重；
- 把身份证、银行卡、家庭等高敏感字段放进普通列表 API；
- 信息更正直接覆盖正式数据，不保留 before/after、理由和审核；
- HR13 职称结果、HR14 岗位聘任结果各自再造一份“当前人员真相”；
- HR03 反过来修改 HR13/HR14 的评审过程记录；
- 把所有教育/工作经历塞进 JSON；
- 把所有证件塞进一个 `additional_info`；
- 允许历史任职区间重叠但没有显式兼岗语义；
- 允许主岗 FTE 合计超过规则仍静默保存；
- 允许跨学校组织/岗位挂到某学校人员；
- 允许下游系统通过知道 staff ID 绕过 data scope；
- Excel 导入逐行 save，失败后留下半成功人员；
- 正式附件用 `/media/...` 裸 URL 长期暴露；
- 用生日、婚姻、身份证等信息做无业务必要的 Dashboard 装饰；
- 为了页面“显得丰富”而在首屏堆几十张卡片。

# 1. 施工前提与依赖

## 1.1 H0 基线硬门

HR03 开始正式建权威模型前必须确认：

- Docker 可重复构建；
- PostgreSQL 迁移可正常执行；
- Django system check 通过；
- GitHub Actions 可执行迁移、专项测试、全量测试；
- 原 Horilla 测试欠账已记录，不能与跃科新增回归混为一谈；
- 生产数据库版本和事务隔离级别已确认；
- 文件中心当前存储方式、安全访问方式和备份方式已审计；
- `django-simple-history / horilla_audit` 的真实能力边界已确认，不能把它误当完整业务审计。

## 1.2 A0 多学校隔离硬门

HR03 是最高敏感域之一。A0 至少必须满足：

- `Company` 已作为学校租户安全边界或已建立等价 tenant root；
- 请求 tenant 由服务端可信上下文解析；
- 无 tenant context 默认 fail-closed；
- 用户只能访问 membership 覆盖的学校；
- HR03 所有权威表必须直接含 `tenant_id` 或具有不可绕过的 tenant FK；
- 所有 FK 写入必须校验同 tenant；
- 搜索、自动补全、历史、导出、附件、纠错、审计均服从同一 tenant/scope；
- 后台任务必须显式 tenant；
- 跨租户批处理只有平台级 `system_scope(reason)` 才能运行；
- `tenant_id=NULL` 不表示“所有学校共享人员数据”；
- 敏感字段访问日志不得跨 tenant 汇总后暴露。

## 1.3 HR02 依赖硬门

HR03 的组织与岗位任职必须引用 HR02 稳定 ID，不允许新模型直接绑 legacy `Department/JobPosition` 作为长期权威外键。

最低依赖：

- `HrOrganization` 稳定 identity 可用；
- `HrPostCatalog/HrPosition` 或等价岗位对象稳定 identity 可用；
- `as_of` 组织有效性查询可用；
- 跨租户组织/岗位 FK 校验可用；
- 组织关闭/迁移可发影响事件；
- 岗位占用/预占接口已定义。

若 HR02 尚未完成，可允许 HR03 UI/Provider 使用 `LEGACY_CURRENT_SNAPSHOT` 做只读预览，但**不得以此迁移成永久 authority ID**。

## 1.4 HR04/HR05 边界

- HR04 管招聘过程；
- HR05 管待入职、材料核验、报到和入职任务；
- HR05 正式确认入职时，调用 HR03 建立/激活 `Person + StaffMaster + EmploymentRelationship + Assignment`；
- HR03 不复制 Candidate/Onboarding 流程状态；
- HR03 只接收“已经生效的人员事实”。

## 1.5 HR06/HR07/HR13/HR14/HR16 边界

HR03 是**权威事实账本与当前投影**，其他模块是**业务过程发起者/裁决者**：

- HR06 调动审批通过 → HR03 关闭旧 Assignment，创建新 Assignment；
- HR07 合同正式生效/终止 → HR03 更新 EmploymentRelationship 的有效事实，不复制合同正文；
- HR13 职称评审生效 → HR03 接收 `ProfessionalTitleAppointmentEffective`，形成可查询投影/事实；
- HR14 岗位聘任生效 → HR03 接收新的岗位任职事实；
- HR16 离职/退休生效 → HR03 关闭关系与 assignment、更新 staff status，但历史不删除。

原则：

> **流程归业务域，生效事实归人员事实层；过程表不是人员当前状态表，人员当前投影也不是过程表。**

## 1.6 HR01 依赖关系

HR03 authority 上线后：

- HR01 在职人数、新进人数、人员类别、学院分布必须从 HR03/HR02 Provider 取；
- 历史 headcount 必须从 EmploymentRelationship/Assignment effective-dated 事实推导；
- HR01 不再用 Horilla `Employee.is_active + date_joining` 反算历史人数；
- HR03 Provider 进入 `AUTHORITY_ONLY` 后，HR01 禁止自动 fallback legacy。

# 2. 三家顶级成熟 HCM 对标结论

本总册吸收 Workday、SAP SuccessFactors、Oracle Fusion HCM 的人员核心思想，但不复制其 UI、代码、命名体系或受保护资产。

## 2.1 Workday：Worker Profile + Effective-Dated Staffing Facts

可吸收的成熟思想：

- Worker Profile 不只是联系信息，而是工作、组织、任职、历史和关联业务的统一入口；
- Job/Position/Profile 等对象具有 effective date；
- Worker History 通过业务事件追溯 Hire、Transfer 等变化；
- 安全权限根据组织和管理角色决定可见范围；
- 资格、技能、教育、经验是结构化背景信息，不应都压进自由文本；
- 业务变更经 Business Process 后再生效，不是任意改当前字段。

转化为跃科 HR03：

- 每个 Staff 有稳定身份页；
- 页面支持 `as_of`；
- 变更事件与当前投影分开；
- 教育/经历/证书结构化；
- 正式变化从业务流程接收生效事件；
- 历史可追溯到“为什么变”。

## 2.2 SAP SuccessFactors：Person 与 Multiple Employments 分离

SAP People Profile 的关键启发：

- Person 级信息与 Employment 级信息是不同层；
- 一个 Person 可以有 multiple employments；
- Profile 可以在多个 employment 之间切换；
- Job Information 是 effective-dated；
- Full Profile 支持选择日期查看 as-of 数据；
- People Profile 把信息拆为 Cards/Categories；
- 权限控制到 effective-dated entities、字段和 target population；
- Concurrent Employment、Contingent Worker 等不是复制一份人档案，而是同一人的不同工作关系。

转化为跃科 HR03：

```text
同一个自然人
    ├─ 正式教职工关系
    ├─ 校内兼岗 assignment
    ├─ 退休返聘关系
    └─ 外聘/项目关系（按学校政策）
```

而不是创建四个 Employee。

## 2.3 Oracle Fusion HCM：Person → Work Relationship → Assignment

Oracle 的核心抽象非常适合我们：

- Person 管自然人信息；
- Work Relationship 管人与雇主/学校之间的聘用关系；
- 一个 Work Relationship 至少一个 Assignment；
- Assignment 描述 job、position、manager、location、hours 等任职事实；
- 支持多个 Assignment；
- Assignment 可以独立做权限裁剪；
- Person/Employment 信息可 date-effective；
- Bulk load 与普通 REST API 应分工，不应拿普通 API 做大批量导入。

转化为跃科 HR03：

> **人员主档必须以 Person + EmploymentRelationship + Assignment 为骨架，而不是 Employee + 当前工作字段。**

# 3. 中国高校业务校正

国际 HCM 的 Person/Employment 模型只能作为底层方法论，中国高校还必须增加高校教师事实维度。

全国教师管理信息相关高校通知长期要求维护：

- 基本信息；
- 学习经历；
- 工作经历；
- 岗位聘任；
- 专业技术职务聘任；
- 教师资格；
- 教育教学；
- 教学科研成果及获奖；
- 人才项目；
- 国内培训/海外研修；
- 技能及证书；
- 联系方式等。

HR03 V1 不负责教学科研成果业务过程，但必须：

1. 建立稳定人员主键，供后续教学科研/教师发展等域关联；
2. 把基本信息、学习经历、工作经历、任职关系、资格证书等基础事实做实；
3. 支持全国教师系统需要的信息映射/数据质量校验；
4. 不能因为某个上报系统字段很多，就把全部字段直接塞进 StaffMaster；
5. 上报维度放到 HR18 映射层，主档只保存真实业务事实。

## 3.1 高校人员的多身份是常态

一个人可能同时是：

- 专任教师；
- 教研室主任；
- 二级学院副院长；
- 专业负责人；
- 班主任/辅导员；
- 科研平台负责人；
- 产业导师/双师型教师；
- 行政管理人员兼课。

这些概念不能全塞到 `employee_type` 一个下拉框。

设计必须分清：

```text
StaffCategory        人员类别
EmploymentType       用工/聘用类型
Assignment           任职关系
RoleTag               业务角色标签/资质投影
ProfessionalTitle     专业技术职务事实
AdministrativeRole   行政职务事实
TeacherQualification 教师资格事实
```

## 3.2 一人一号不是“一人一个账号”

高校主档需要稳定教职工编号，但：

- staff_no 是学校业务编号；
- person_uid 是系统稳定自然人 ID；
- account_id 是登录账号；
- SSO subject 是外部身份标识；
- national_id 是敏感证件号；
- email/phone 只是联系方式。

禁止互相替代。

## 3.3 历史事实必须优先于当前表便利性

今天教师从计算机学院调到人工智能学院：

- 当前主档显示人工智能学院；
- 2024 年考核仍显示计算机学院；
- 2024 年教学/职称/合同/审批历史不能因为当前变更而重写；
- `as_of=2024-12-31` 必须恢复当时组织和岗位；
- 组织名称改过，也必须通过 HR02 as-of 解析当时名称。

# 4. Horilla 2.0 现状审计与接管判断

## 4.1 可利用的基础

Horilla 当前已有：

- `Employee` 基础人员模型；
- `EmployeeWorkInformation` 当前工作信息；
- Employee 列表、卡片、详情、编辑；
- Employee/WorkInformation Excel import/export；
- 基础过滤/分页；
- `horilla_documents.Document/DocumentRequest`；
- `HorillaAuditLog` / `django-simple-history`；
- profile image 校验；
- permissions / groups；
- notifications；
- onboarding/offboarding/recruitment 关联。

这些代码有很高的**交互与迁移参考价值**。

## 4.2 `Employee` 当前问题

当前 Employee 直接保存：

- badge_id；
- account OneToOne；
- 姓名；
- email（全局 unique）；
- phone/address；
- DOB/gender/marital；
- qualification；
- experience；
- emergency contact；
- is_active；
- additional_info JSON。

主要问题：

1. Person 与 Staff 身份没有分层；
2. email 全局唯一不适合作为多学校/多关系权威身份；
3. qualification/experience 是扁平当前字段，无法表达多条经历；
4. `is_active` 太粗；
5. `additional_info` 容易演变成不可治理 JSON 黑洞；
6. Account 与 Employee 绑定太紧；
7. Employee 创建时甚至会自动创建 User，说明模型与账号生命周期强耦合；
8. 当前模型不支持一个 Person 多 EmploymentRelationship。

结论：**REWRITE 权威层，Employee 保留为 Legacy Projection。**

## 4.3 `EmployeeWorkInformation` 当前问题

当前 WorkInformation 是 OneToOne Employee，直接保存：

- department；
- job position；
- job role；
- reporting manager；
- shift；
- work type；
- employee type；
- company；
- work email/mobile；
- date_joining；
- contract_end_date；
- basic_salary/salary_hour；
- additional_info；
- audit history。

这是典型“当前快照”模型。

它无法可靠表达：

- 多 assignment；
- 主岗/兼岗；
- 组织任职历史；
- 返聘/再次入职；
- 多次 Employment Relationship；
- 某日期的真实岗位；
- retroactive correction；
- 部门/岗位未来生效；
- assignment 级 data scope。

结论：**只保留 legacy compatibility，不再承载新权威事实。**

## 4.4 Horilla Documents 接管判断

现有 Document 有：

- employee FK；
- request；
- file；
- status；
- issue/expiry date；
- notify_before；
- 文件扩展名校验。

值得 KEEP/ADAPT 的是：

- 文件上传底层；
- DocumentRequest 任务思想；
- 格式/大小安全校验；
- 过期提醒基础。

必须 NEW/REWRITE 的是：

- 证据材料分类；
- 文件 SHA-256；
- 材料版本；
- business fact 绑定；
- 来源与核验人；
- 敏感等级；
- 受控预览/下载票据；
- 水印；
- 替换/作废历史；
- retention；
- purpose/audit。

## 4.5 Horilla Audit 接管判断

现有 `HorillaAuditLog` 可提供模型历史记录，但存在：

- 依赖 request thread；
- signal 中宽泛 try/except；
- 业务原因、审批实例、数据来源不是强制字段；
- 不等同于“敏感信息查看审计”；
- 不等同于“正式业务事件账本”。

结论：

```text
simple-history / HorillaAuditLog   KEEP 作为技术历史辅助
HrStaffAuditEvent                  NEW 作为正式人员业务审计
SensitiveAccessLog                 NEW 作为敏感查看/导出审计
```

## 4.6 Horilla Import/Export 接管判断

当前 views 已有 pandas、Excel 导入导出、error report 等基础，但 HR03 正式导入必须重建为异步 staging 体系，禁止同步逐行 save。

接管策略：

| Horilla 能力 | HR03 决策 |
|---|---|
| Employee list/filter | ADAPT UI/查询经验 |
| Employee current model | LEGACY PROJECTION |
| EmployeeWorkInformation | LEGACY PROJECTION |
| profile page | REWRITE |
| import/export helpers | ADAPT 技术思路，REWRITE 业务合同 |
| Document storage | ADAPT |
| Audit history | KEEP + NEW 正式审计 |
| notification | KEEP/ADAPT |
| account creation in Employee.save | REMOVE FROM AUTHORITY FLOW |
| badge_id generation | ADAPT 为 tenant-scoped staff_no service |
| additional_info | REMOVE 作为正式核心字段容器 |

# 5. HR03 信息架构冻结

HR03 固定六个三级工作区：

```text
HR03 教职工主档
├─ HR03-01 教职工名册
├─ HR03-02 教职工主档
├─ HR03-03 任职与身份履历
├─ HR03-04 教育资格履历
├─ HR03-05 人事材料档案
└─ HR03-06 信息更正与历史
```

不再新增同层级菜单。

后续需求优先进入六个工作区内部 Tabs/Section，除非出现完全独立的高频闭环，否则禁止菜单膨胀。

## 5.1 一级入口原则

HR03 默认入口为 **HR03-01 教职工名册**，因为人事人员最常见动作是“找人”。

从名册点入人员后进入 HR03-02 主档，再通过统一 Profile Nav 进入其余四类履历/材料/历史。

## 5.2 非重复原则

- HR03-02 不重复做完整材料库，只显示材料摘要；
- HR03-03 不做调动审批，调动入口去 HR06；
- HR03-04 不做双师认定流程，去 HR09；
- HR03-05 不做通用全系统文件中心；
- HR03-06 不允许用“更正”替代正式调动、职称、岗位聘任、合同变更。

# 6. 角色模型

## 6.1 核心角色

### 学校人事管理员 HR_ADMIN

- 全校基础人事范围；
- 可查看普通敏感字段；
- 特高敏字段按独立 permission；
- 可创建/维护主档；
- 可审核更正；
- 可导入导出；
- 不天然拥有平台跨学校权限。

### 人事负责人 HR_DIRECTOR

- 学校级；
- 可审批高风险更正；
- 可查看重要数据质量和历史影响；
- 可处理 retroactive correction。

### 学院人事秘书 COLLEGE_HR

- 仅授权学院 scope；
- 可看本学院人员业务字段；
- 高敏字段默认不可见；
- 可发起补充/更正；
- 是否可新增人员由学校配置，默认不能绕过 HR05 入职创建正式 ACTIVE 人员。

### 部门负责人 UNIT_MANAGER

- 仅管理关系或指定范围；
- 主要看任职、联系方式、必要资格；
- 不看身份证、银行卡等高敏字段。

### 教职工 STAFF_SELF

- 只能看本人可开放字段；
- 可发起自助更正；
- 不直接修改权威字段；
- 可上传指定材料。

### 审计/安全 AUDITOR

- 可查访问日志、变更历史；
- 默认不等于可看全部明文敏感数据。

### 平台运维 PLATFORM_OPERATOR

- 维护 SaaS 平台；
- 默认不能读取学校人员明文敏感数据；
- 故障处理需要 break-glass 受控授权与审计。

## 6.2 数据范围

固定 scope type：

```text
SCHOOL
COLLEGE
DEPARTMENT
ASSIGNMENT
SELF
EXPLICIT_STAFF_SET
```

必须先 tenant，再 data scope，再 permission，再字段级策略。

## 6.3 字段权限等级

```text
PUBLIC_HR       普通人事字段
RESTRICTED_HR   受限字段
SENSITIVE       敏感字段
HIGH_SENSITIVE  高敏感字段
```

例：

| 字段 | 默认等级 |
|---|---|
| 姓名/工号/学院/岗位 | PUBLIC_HR |
| 手机/私人邮箱/家庭地址 | RESTRICTED_HR |
| 出生日期/婚姻/紧急联系人 | SENSITIVE |
| 身份证号/护照号/银行卡 | HIGH_SENSITIVE |

权限必须由服务端裁剪，禁止“前端拿到明文再遮罩”。

# 8. 稳定身份、去重与账号解耦

## 8.1 Person UID

`person_uid` 使用 UUID/ULID 等稳定不可变技术 ID。

永远不要用：

- email；
- phone；
- ID card 明文；
- employee database auto increment；
- SSO username；

作为跨域永久身份。

## 8.2 Staff No

staff_no：

- tenant scoped；
- 由独立 StaffNumberService 生成；
- 规则可配置前缀/长度；
- 已使用编号默认不回收；
- 返聘原则上保留原 staff_no 还是新编号由学校规则决定，但 Person 不变；
- 规则变更不重写历史人员编号。

## 8.3 身份证件

新增：

```text
HrPersonIdentityDocument
- id
- tenant_id
- person_id
- document_type
- document_number_ciphertext
- document_number_fingerprint
- masked_display
- issuing_country
- valid_from
- valid_to
- verification_status
```

要求：

- 明文加密存储；
- 检索去重使用 tenant-aware fingerprint/hash；
- API 默认只返回 masked_display；
- 明文查看必须独立 permission + purpose + audit；
- 日志禁止打印明文。

## 8.4 去重策略

创建/导入人员时按风险分层：

```text
HARD_MATCH
  同租户 + 同证件 fingerprint

LIKELY_MATCH
  姓名 + 出生日期 + 手机/邮箱/历史工号等组合

NO_MATCH
```

LIKELY_MATCH 不允许系统自动合并，进入人工去重确认。

## 8.5 Account 解耦

```text
HrStaffMaster 1 --- 0..n HrAccountLink --- Auth User/SSO Identity
```

人员可以：

- 尚未开账号；
- 账号停用但人员历史仍在；
- 更换账号；
- 有外部 SSO mapping；
- 离职后账号回收但主档永久保留。

禁止 HR03 authority model `save()` 自动创建密码账号。

# 9. 生效期、业务变更与数据更正

## 9.1 时间区间语义

统一使用半开区间：

```text
[effective_from, effective_to)
```

例如：

```text
2024-09-01 <= as_of < 2026-02-01
```

`effective_to = NULL` 表示开放结束。

所有 as-of 查询由统一 `EffectiveDatedQueryService` 实现，禁止各页面自己拼日期条件。

## 9.2 三种变化必须区分

### BUSINESS_CHANGE 业务变化

现实世界真的发生了新事实，例如调动、岗位变化、返聘。

处理：关闭旧 segment，新增新 segment。

### CORRECTION 数据更正

现实世界没变化，只是系统原数据录错。

处理：通过 CorrectionCase 修正事实，并保留完整 before/after 和理由。

### RETROACTIVE_CHANGE 追溯生效变化

业务决定在过去日期生效。

必须做影响分析：

- 是否影响已发工资；
- 已归档考核；
- 已完成职称；
- 已发布教学事实；
- 数据上报；
- HR01 历史指标。

高风险情况需要更高权限审批。

## 9.3 未来生效

支持未来：

- 调动；
- 转岗；
- 人员类别变化；
- 退休；
- 返聘。

UI 必须明确区分：

```text
当前有效
未来已计划
历史已结束
```

`assignment_type`：

```text

CONCURRENT
TEMPORARY
SECONDMENT
```

## 12.6 主岗规则

- PRIMARY 结束前新 PRIMARY 生效必须原子关闭旧段；
- 并发修改需 row lock/version。

```http
GET /api/hr/v1/staff/{id}/employment-relationships
GET /api/hr/v1/staff/{id}/timeline
```

正式写 API 主要供业务域 service 调用，不直接暴露成普通前端 CRUD：


或更推荐 domain service + outbox consumer。

## 15.1 核心原则

- 原值是什么；

- 谁审核；
- 哪一天生效；
- 是否影响历史和下游；
- 是否已经写入 authority；
- 是否需要重算/通知下游。

## 15.2 Field Governance Policy

新增：

```text

- field_code
- edit_mode
- required_permission
- required_evidence
- approval_policy
- sensitivity_level
- retroactive_allowed
```

`edit_mode`：


## 15.3 Correction 状态机

```text

→ SUBMITTED
→ UNDER_REVIEW
→ RETURNED → RESUBMITTED

→ REJECTED
→ CANCELLED
```

- RETURNED ≠ REJECTED；
- APPROVED 后应用失败必须 `APPLYING/FAILED` 可追踪；
- 不允许审批成功但实际主档没改而仍显示 success。

# 21. 关键领域不变量（必须写成测试）

1. Person UID 永不因组织/账号变化而改变；
2. 同 tenant staff_no 唯一；
3. 同 tenant Person 不得无意创建重复 StaffMaster；
4. 一个 EmploymentRelationship 至少有一个生效 Assignment 才能进入 ACTIVE（可按入职时间阶段）；
5. 同一关系同一日期默认最多一个 PRIMARY assignment；
6. Assignment organization/position 必须同 tenant；
7. Assignment position 在 as_of 必须有效；
8. POSITION_CONTROL 岗位不能超占；
9. EmploymentRelationship 结束后不能存在超出结束日期的 active assignment；
10. 正式离职不能 DELETE Person/Staff；
11. Correction 不能绕过业务域改变 BUSINESS_PROCESS_ONLY 字段；
12. 历史 as-of 不能读取 current projection 替代历史；
13. 高敏字段无 permission 不得出现在 API payload；
14. 高敏 reveal 必须审计；
15. 材料跨 tenant 永远拒绝；
16. 材料旧版本不可无痕覆盖；
17. Excel commit 全批次原子或按定义可恢复，不得未知半成功；
18. Authority 模式后不得自动 fallback legacy；
19. 账号删除/停用不删除人员事实；
20. rehire 优先关联已有 Person，不无意创建新 Person。

# 22. 人员状态机

人员状态不能只用 `is_active`。

建议：

```text
PENDING_ENTRY
ACTIVE
SUSPENDED          特殊停职/暂停关系，是否使用按学校政策
DEPARTURE_PENDING
DEPARTED
RETIRED
RETIRED_REHIRED    可由 relationship 投影，也可不用单独状态
```

实际推荐 `Staff current status` 是关系推导投影，权威仍是 EmploymentRelationship segments。

注意：

- 请假不改变 employment status；

# 25. 数据新鲜度与缓存

继承 HR01 终极版规则。

HR03 的核心人员详情原则上偏实时，缓存要非常克制。

## 25.1 建议新鲜度

| 数据 | TTL | maxStaleSeconds | hardExpire |
|---|---:|---:|---:|
| Staff header/current assignment | 30s | 60s | 300s |
| 名册统计数字 | 60s | 180s | 600s |
| 背景履历 | 120s | 300s | 1800s |
| 历史 timeline | 300s | 900s | 3600s |
| 材料元数据 | 60s | 180s | 600s |

写入成功后优先事件失效，而不是等 TTL。

## 25.2 cache key

必须包含：

```text
tenant
user/dataScope hash
staffId
asOf
permission profile hash（必要时）
authorityMode
schemaVersion
```

严禁不同权限用户共享带敏感字段的完整 profile cache。

## 25.3 缓存失败语义

可以 stale-on-error 的只有低风险摘要；高敏/关键当前任职如果 hard expired，应返回 unavailable/error，不拿几小时前旧数据冒充当前权威。

# 31. LegacyDataMapping：Horilla → HR03

S0/S1 必须生成并维护 `docs/hr03/LegacyDataMapping.md`。

基础映射：

| Horilla | 新权威 | 说明 |
|---|---|---|
| `Employee.id` | `HrStaffMaster.legacy_employee_id` | 只作映射 |
| `Employee.badge_id` | `HrStaffMaster.staff_no` | 经冲突/格式校验迁移 |
| first/last name | `HrPerson.legal_name` | 迁移前中文姓名拼接规则确认 |
| `Employee.email` | PersonContact / AccountLink | 不再做 person unique |
| `Employee.phone` | PersonContact | 敏感策略 |
| dob/gender | HrPerson | 数据质量校验 |
| qualification | background migration candidate | 不直接认权威学历 |
| experience numeric | 不迁为经历事实 | 只能作为 legacy reference |
| emergency contact | HrEmergencyContact/受限字段 | 可后续独立模型 |
| `is_active` | migration hint | 不能直接等于新 status |
| `EmployeeWorkInformation.company_id` | tenant mapping | 必须 A0 校验 |
| department | HrStaffAssignment.organization_id | 通过 HR02 legacy mapping |
| job_position | HrStaffAssignment.position/post | 通过 HR02 mapping |
| job_role | assignment role candidate | 逐校规则核验 |
| employee_type | staff/employment category mapping | 字典映射 |
| date_joining | EmploymentRelationship.effective_from | 需对账 |
| contract_end_date | HR07 contract reference | 不作为 HR03 合同权威 |
| basic_salary | HR15 migration reference | HR03 不接管工资权威 |
| Document | HrStaffMaterialVersion legacy link | 分类需人工/规则映射 |

## 31.1 禁止自动“猜正确”

以下 legacy 数据不能自动硬迁：

- qualification 字符串 → 最高学历；
- experience 数字 → 工作经历；
- JobRole → 高校岗位等级；
- Department 名称 → 新组织，仅按名字模糊匹配；
- employee_type → 专任教师等高校类别，没有映射规则；
- `is_active=False` → 一律离职。

这些进入 mapping/exception queue。

# 32. Legacy 退出合同

模式：

```text
LEGACY_STAFF_ONLY
DUAL_READ_COMPARE
HR03_AUTHORITY
```

## 32.1 LEGACY_STAFF_ONLY

- 旧 Employee 仍服务原模块；
- 新 HR03 只做影子/迁移验证；
- 不对外宣称 authority。

## 32.2 DUAL_READ_COMPARE

同一 staff 同时读：

- Horilla 当前快照；
- HR03 authority projection。

对比：

- staff_no；
- current org；
- current position；
- employee type；
- date joining；
- status；
- work contact。

Mismatch 必须进对账中心，不能静默忽略。

## 32.3 HR03_AUTHORITY

进入条件：

- mapping 完成率达到门槛；
- 关键字段 mismatch = 0 或全部有已接受 exception；
- 下游 provider 已切换；
- 回归全绿。

进入后：

> **禁止新 HR03 Provider 故障时自动 fallback 到 Employee/EmployeeWorkInformation。**

Legacy projection 只能作为兼容写出，不再作为权威读源。

## 32.4 Authority → Legacy Projection

为了继续复用 Horilla Attendance/Leave/Payroll 等尚未改造模块，可以由：

```text
HrLegacyEmployeeProjectionService
```

受控更新：

- Employee 当前姓名/联系投影；
- WorkInformation 当前组织/岗位/类型投影；

要求：

- 单向 authority → legacy；
- projection failure 可重试；
- 有 reconciliation；
- 不允许 legacy edit 自动反向覆盖 authority。

## 32.5 Email 全局唯一风险

Horilla `Employee.email` 当前全局 unique 是多学校/同人多关系潜在阻断。

A0/HR03 必须明确解决：

优先方案：

- legacy Employee 增加 tenant-aware identity/projection 设计，解除 email 作为跨租户 business unique 的假设；
- Auth User 与 PersonContact 分离。

在此问题未解决前，不允许为通过 unique constraint 人为生成“假业务邮箱”并让用户看到。

# 49. 自纠错复核

## 49.1 是否把 HR03 做得太“大而全”？

纠正：六个三级模块只覆盖人员基础事实。职称、双师、培训、合同等流程仍归独立域；HR03只接收生效事实/投影。

## 49.2 是否为了历史正确引入过多模型？

结论：Person / Staff / Relationship / Assignment 是成熟 HCM 的基础分层，不能再压缩成一张表；背景履历可适度共用抽象，但不要万能 JSON。

## 49.3 是否需要 Person 跨学校全局合并？

V1 不建议平台自动跨学校识别/合并自然人，这会引入严重隐私和租户边界问题。

正确策略：

- Person 默认 tenant-private 语义或 tenant 受控映射；
- 如果未来做平台级跨校人才身份，需要单独隐私与授权架构；
- 不能因为身份证相同就在 SaaS 后台自动把 A 校、B 校人员暴露给彼此。

实现上可让 `HrPerson` 含 tenant_id，或建立 tenant-private Person namespace。**本项目 V1 推荐 `HrPerson.tenant_id` 直接存在，避免跨租户 Person 共享。**

这是本版对国际 HCM “global person”抽象做的中国 SaaS 隐私校正。

## 49.4 StaffMaster 是否要存 current fields？

可以存少量投影提升性能，但必须可重建、不可作为历史 authority。

## 49.5 教育/资格谁能改？

不是所有 HR 用户都直接改。必须 FieldGovernancePolicy。

## 49.6 敏感字段应用层加密是否一次做到底？

不能为了“安全感”随意引入无法检索/无法运维的自研加密。V1 应先确定威胁模型、KMS/密钥轮换、备份恢复，再决定应用层加密范围。无论如何 API/日志/权限/审计必须先做到。

# 52. 终极补强：前 1% 设计约束

## 52.1 Person Merge / Unmerge 必须提前留架构位

人员去重最终会出现“两个历史 Employee 实际是同一个人”。

V1 可以不开放普通 UI merge，但模型必须支持正式治理流程：

```text
HrPersonMergeCase
- source_person_id
- target_person_id
- reason
- evidence
- status
- approved_by
- applied_at
```

合并不能简单 DELETE source：

- 保留 alias/mapping；
- 记录旧 ID → 新 ID；
- 下游重定向；
- 支持错误合并的受控逆向处理设计。

## 52.2 Deceased / 法定特殊状态

不要用“离职”表达所有终止关系。人员自然人状态与 employment 结束原因分开。V1 可只保留原因字典架构，不必做独立菜单。

## 52.3 数据来源可信度

每个高价值事实支持：

```text
source = SELF_REPORTED / HR_ENTERED / MIGRATED / VERIFIED_EXTERNAL / BUSINESS_PROCESS
verification_status
verified_by
verified_at
```

UI 对未核验内容展示“待核验”，避免和正式核验事实视觉等价。

## 52.4 Snapshot Hash

对正式导出/上报/归档时，可生成 Profile Snapshot + hash，证明“当时上报的是哪一版人员事实”。

这对 HR18 数据上报、审计非常有价值。

## 52.5 关闭期保护

当某些历史期间已被：

- 工资封账；
- 年度考核归档；
- 职称材料归档；
- 上报冻结；

HR03 retroactive correction 必须显示冲击，并可能需要对应域解冻/补差，而不是静默重算。

## 52.6 读模型与写模型分离

名册和 Profile 可使用 `HrStaffCurrentView` / materialized/read projection，但：

- authority 仍是事实表；
- projection 有版本；
- 可重建；
- 有 lag 监控；
- 不直接写 projection。

## 52.7 PII 最小化

“系统能存”不等于“必须存”。

每个字段进入 StaffMaster 前问：

1. 哪个业务场景使用？
2. 哪个法规/学校制度要求？
3. 谁能看？
4. 保留多久？
5. 可否放材料而不是结构化明文？

# 57. 一句话冻结

> **HR03 的目标不是做一张更漂亮的员工表，而是把 Horilla 的“当前 Employee 快照”升级为高校可售、可审计、可追溯、可按日期还原、可支撑 15 年人员生命周期的权威教职工事实底座；前端必须像顶级 HCM 一样让用户看到一个清晰可信的人，后端必须像事实账本一样永远不把历史改坏。**
