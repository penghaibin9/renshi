## 0. 文档裁决顺序

发生冲突时，严格按下面顺序裁决：

```text
1. 当前 Git exact HEAD + 当前 PR 的 CI / 测试 / 浏览器 / 运行证据
2. CURRENT_STATE_2026-09-04.md
3. CORE_BUSINESS_FLOW_ACCEPTANCE.md
4. 开发顺序_接管版.md
5. 00 全局架构合同 + 99 总控总册
6. 对应 HRxx 业务施工总册
7. GAP / TASK / RISK / Legacy Mapping
8. 历史 READY / FINAL / Acceptance / CURRENT_STATE 快照
```

必须记住：

- 文档写了 `READY`，但当前 HEAD 红灯，结论仍是 **NOT READY**。
- 页面能打开、按钮能点、出现成功提示，不能证明业务已经办结。
- MySQL、租户隔离、权限、审计、状态历史、幂等、并发和恢复证据缺一项，不能写 `PRODUCTION READY`。
- `CURRENT_STATE_2026-08-10.md` 等旧日期文件只作为历史快照保留，不再指导当前施工。

## 5. `docs/hr/`、Legacy 与历史资料怎么用

### `docs/hr/`

常见文件：

```text
*_GAP_MATRIX       目标与代码差距
*_TASK_TREE        阶段任务树
*_RISK_REGISTER    风险登记
*_Sxx_*            某个历史 SHA 的阶段验收记录
```

它们用于定位问题，不覆盖当前代码事实。

### `docs/hr/legacy/`

只回答旧 Horilla 数据如何映射、迁移、对账、退出；不能继续把 Legacy 模型当成新业务 Authority。正式 Cutover 后必须达到：

```text
LEGACY FORMAL WRITES = 0
```

### 旧状态与旧验收报告

带日期或 `FINAL/READY/Acceptance` 的旧文件必须按“当时 SHA 的证据”理解。没有 exact SHA、测试链接或当前回归结果的报告，不能用于上线签字。

## 6. 什么叫文档完成

`docs/` 只有同时满足下面条件才算完成：

- 入口、当前状态、施工顺序、业务总册、验收标准和运维手册职责不重叠；
- 所有“当前”表述与真实代码目录、数据库、工作流和 PR 一致；
- 每个生产结论可追到 40 位 Git SHA 和可复现命令/Actions；
- 历史文档被明确标成历史，不会误导新手继续旧施工顺序；
- 业务流程定义包含角色、状态变化、刷新回读、另一端回读和历史留痕；
- 权限、租户、并发、幂等、文件、Excel、审计、备份恢复不以“后续再做”省略；
- 代码发生契约变化时，优先改唯一 Authority 总册和当前状态，不复制新版本说明书。
