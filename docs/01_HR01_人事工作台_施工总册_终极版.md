## 0. 结论先行

HR01 不是“做一个漂亮 Dashboard”，而是整个人事系统的**运营控制台（HR Control Center）**。

它必须同时回答五个问题：

1. **学校现在的人事状态是什么？** —— HR01-01 人事总览
2. **我现在最该处理什么？** —— HR01-02 我的待办
3. **什么事情如果不处理会出问题？** —— HR01-03 人事预警
4. **这支教师队伍的结构健康不健康？** —— HR01-04 队伍结构
5. **我要办一件高频人事业务，从哪里立即开始？** —— HR01-05 快捷办理

顶级人事工作台的核心不是图多，而是：

> **可信事实 → 明确结论 → 风险排序 → 一键钻取 → 进入真实业务动作 → 全程权限与审计闭环。**

因此本模块禁止以下低质量实现：

- 只做 KPI 卡片和饼图；
- 用前端数组聚合正式数据；
- 下游模块失败时把数字默认为 0；
- 指标不可解释、无统计口径；
- 数字可看但不能钻取；
- 待办和预警只是消息列表，不能进入业务；
- 多学校账号未明确学校上下文就返回数据；
- 把当前 `Employee.is_active` 反推历史人数；
- 把生日提醒当人事管理核心风险；
- 在模板中继续堆 1000 行内联 CSS；
- 从 CDN 动态加载核心图表库；
- 新增大量一次性组件，导致后续 HR02-HR18 UI 各长各的；
- 为了“首页好看”读取工资、身份证等不必要敏感字段。

# 1. 施工前提与依赖

## 1.1 必须先满足的硬前提

HR01 可以先设计、可以先搭公共 UI、Provider Contract 和 Legacy Adapter，但要宣称“生产封板”必须满足以下前提。

### H0 基线

- Docker 可重复构建；
- PostgreSQL 迁移一致；
- Django system check 通过；
- 基础 health/readiness 通过；
- 已知 Horilla 上游测试欠账被区分为“上游欠账 / 跃科新增回归”，不得用跳过测试伪造全绿。

### A0 多学校隔离

- 当前学校 `tenant/school` 上下文解析完成；
- 无学校上下文默认 fail-closed；
- 用户只能选择自己有 membership 的学校；
- 学校 A 数据绝不能通过 ID、筛选、导出、图表钻取看到学校 B；
- 后台任务明确 school scope；
- 聚合指标与明细钻取使用**同一数据范围合同**；
- 学校时区进入 `HrRequestContext`，禁止用服务器本地时间直接定义“今天/本月/本年”。

### HR02 / HR03 事实依赖

HR01 的完整生产口径依赖：

- HR02：高校组织机构 / 编制 / 岗位事实；
- HR03：教职工主档 / 任职关系 / effective-dated 历史事实。

在 HR02/HR03 完成前，可以提供 `LegacyHorillaEmployeeProvider`，但所有 legacy 指标必须明确：

```text
dataBasis = LEGACY_CURRENT_SNAPSHOT
```

不得用 legacy 当前状态数据伪装“历史事实”。

### S3 前新增硬门：LegacyDataMapping 必须先完成

**在 HR01-S3“人事总览”正式编码前，必须先物化并评审：**

```text
docs/hr/legacy/LegacyDataMapping.md
```

该文档至少列出：

- Horilla 当前模型/字段；
- 当前业务含义；
- 未来 HR02/HR03/HR07/HR11/HR15 权威模型归属；
- 迁移方式：`MIGRATE / PROJECT / COMPAT_ONLY / DEFER / DROP_AFTER_CUTOVER`；
- 数据清洗规则；
- 唯一键/去重规则；
- tenant 映射；
- 历史可追溯能力是否存在；
- 切换前后读写权威关系；
- 验证 SQL/测试口径；
- 回滚限制。

本总册第 30 节给出初始权威映射，编码 AI 必须以仓库实际字段再次核对后物化，不允许凭印象迁移。

### Legacy Provider 退出合同必须先设计

在 HR02/HR03 上线后，禁止出现“新模型已经写入，但首页仍偶尔从旧 Employee 表取值”的幽灵状态。

因此必须支持：

```text
LEGACY_ONLY
    ↓
DUAL_READ_COMPARE
    ↓
AUTHORITY_ONLY
```

进入 `AUTHORITY_ONLY` 后：

- 生产代码禁止自动 fallback 到 LegacyProvider；
- legacy fallback 被调用必须抛出明确错误并记录审计/监控；
- 不得为了首页继续有数字而静默读取旧表；
- 如需紧急回滚，只能由受控的迁移开关显式执行，并留下操作者、原因、时间和差异证据。

## 1.2 HR01 的边界

HR01 只负责：

- 聚合；
- 判断；
- 展示；
- 预警；
- 待办汇聚；
- 快捷导航；
- 轻量 acknowledge/snooze（仅限预警中心自己的状态）。

HR01 **不负责**：

- 招聘审批业务状态机；
- 合同续签业务状态机；
- 请假审批业务状态机；
- 职称评审业务状态机；
- 工资计算；
- 教职工档案正式写入；
- 组织岗位正式写入。

任何真正业务动作应调用**业务域自己的 service/API**，而不是 HR01 自己直接 UPDATE 对方表。

## 1.3 施工优先级原则

HR01 的代码施工必须遵循：

> **事实正确性 > 租户与权限 > 迁移边界 > 可观测性 > 性能 > UI 精致度。**

UI 必须顶级，但不允许通过牺牲事实、权限、可解释性来换取“看起来很完整”。

# 2. 三家顶级成熟 HCM 对标结论

本总册对标三个国际成熟 HCM 产品的“首页 / 人员分析 / 预警与行动”思想，并结合中国高校公开建设需求重新设计，不复制其代码、视觉资产或受保护界面。

## 2.1 Workday

可吸收的核心思想：

- 分析与事务在同一套可信数据中运行；
- 实时数据而不是离线手工报表；
- 角色化安全控制；
- 首页提供个性化任务、交易、报告和洞察；
- KPI 可以继续钻取；
- “看到问题 → 立即行动”，不让用户从分析页再到处找菜单；
- Dashboard 不是静态大屏，而是工作入口。

### 转化为跃科 HR01

- 所有 KPI 有 drilldown；
- KPI 与明细使用同一 selector 和 scope；
- 待办/预警直接深链到具体业务对象；
- 首页根据权限和角色变化；
- 数据更新时间和口径可见；
- 不建设第二套“报表数据库真相”。

---

## 2.2 SAP SuccessFactors

可吸收的核心思想：

- Workforce Analytics 指标应有统一公式；
- Role-Based Permissions 同时控制分析能力；
- 合同到期、流程卡住、HR 数据问题都可产生 Alert；
- 首页以 Take Action 卡驱动处理；
- Admin Alerts 聚合流程、数据、集成等异常；
- Alert 的消息、接收人、触发规则分离；
- 警报规则必须经过测试，避免提醒风暴。

### 转化为跃科 HR01

- 建立 `MetricDefinitionRegistry`，每个 KPI 都有定义版本；
- 预警分为规则、实例、接收人和状态；
- 同类风险聚合展示但能展开到具体对象；
- 严禁“每晚扫库然后无限重复发消息”；
- 支持去重、首次发现、最后发现、确认、已处理、失效；
- 预警页不仅看“红点”，还要看“风险为什么产生、由谁处理、截止日期”。

---

## 2.3 Oracle Fusion HCM Analytics

可吸收的核心思想：

- 预构建 KPI 体系，而不是每个客户重新拼 SQL；
- 人数、入职、调动、晋升、离职、缺勤等均是可比较的劳动力指标；
- 人数增加和减少必须区分原因；
- 组织健康要看趋势，不只看某天静态总量；
- 任何分析都必须服从安全范围；
- 人力分析可以跨维度钻取；
- 分析必须围绕“业务问题”设计，而不是围绕数据库字段设计。

### 转化为跃科 HR01

- 工作台指标采用固定“高校人事 KPI 字典”；
- 结构分析优先回答学校真实管理问题；
- `headcount_gain / headcount_loss / net_change` 独立定义；
- 历史趋势必须基于 effective-dated 事实；
- 领导看汇总、人事处看明细、二级学院看本学院；
- 不允许前端自行拼出另一个统计口径。

---

## 2.4 三家共同精华：HR01 的八条产品原则

1. **一个可信事实源**
2. **角色化与数据范围先于 UI**
3. **指标有定义、有版本、有时间口径**
4. **实时/近实时，并显示数据新鲜度**
5. **看到数字能钻取**
6. **看到风险能行动**
7. **异常比漂亮图表更优先**
8. **首页是“控制台”，不是“BI 展板”**

# 3. 中国高校业务校正

高校人事工作台与普通企业 HR 最大区别：

- 组织是“学校—学院—系部/科室”，还可能有党政双组织；
- 教职工同时存在职务、职称、岗位等级、教师资格、双师、专兼职等多身份；
- 高职必须关注双师型、企业实践、外聘/产业教师；
- 年度考核和聘期考核都是正式人事事实；
- 人事处需要编制 / 岗位 / 职数视角；
- 合同、退休、资格复核、数据上报都有强时限风险；
- 需要面向二级学院人事秘书和校领导提供不同工作台；
- 需要对接财务、统一身份、教务、数据中台；
- 数据上报、全国教师信息更新是持续运营动作，不是一次性项目。

因此 HR01 的核心 KPI 不采用普通企业“员工满意度、销售人员离职率”模板，而采用高校人事口径。

## 4.2 当前实现的生产级缺陷

### P0-01：指标只有 `login_required`，缺乏 HR01 独立权限合同

当前 dashboard view/API 主要只验证已登录。

风险：

- “登录”不等于“可以看全校人事统计”；
- 校领导、人事处、学院秘书、普通教师的数据视野完全不同；
- 未来多学校必须 tenant + permission + data scope 三层同时生效。

**裁决：REWRITE 权限层。**

---

### P0-02：历史 headcount 算法不成立

当前 `employee_headcount_trend()` 使用：

- 当前 `employee_id__is_active=True`
- `date_joining <= month_end`

去计算过去月份人数。

这会造成：

> 今天已经离职的人，在过去真实在职月份被错误排除；  
> 今天还在职的人，只要当时已入职，就一直计入；  
> 历史月份无法反映当时真实的人事状态。

**裁决：生产历史趋势必须等待/使用 HR03 effective-dated EmploymentRelation。**

---

### P0-03：异常被 `except Exception: pass` 吞掉

当前请假数量和生日逻辑存在宽泛异常吞掉。

结果：

- leave 服务失败可能显示 `0`；
- 数据错误可能显示“无人请假”；
- 用户无法区分“真的 0”和“系统没算出来”。

**裁决：禁止 fail-open / fake-zero。**

统一使用：

- `OK`
- `PARTIAL`
- `UNAVAILABLE`
- `STALE`
- `ERROR`

---

### P1-01：前端请求碎片化

现有 dashboard 拆成多个小 JSON API，容易形成首页 waterfall：

- KPI
- department
- gender
- type
- position
- joining trend
- headcount trend
- recent
- birthday

**裁决：首屏改为 bootstrap 聚合接口 + 非首屏 lazy section。**

---

### P1-02：模板内联 CSS 过重

当前 dashboard 将大量 CSS 和页面逻辑直接写在模板中。

问题：

- 无法形成 18 个模块统一设计语言；
- 同一 KPI 卡、Panel、Empty State 会被重复造；
- 改品牌主题成本高；
- 无稳定视觉回归边界。

**裁决：建立跃科 HR UI Design System。**

---

### P1-03：核心图表从 CDN 运行时加载

生产环境不应该把核心人事首页是否可用交给公共 CDN。

**裁决：ApexCharts 固定版本本地打包/静态托管。**

本模块不强制换图表库。走捷径时优先保留 ApexCharts，但必须封装成公共组件。

---

### P1-04：“最近员工”排序口径不专业

当前 `recent` 以 `-id` 为主，并不等于最近入职。

**裁决：如果保留，必须按正式 `date_joining/effective_from` 排序。**

V1 首页不把“最近员工”作为首屏核心；改为“本月新进 / 待入职 / 最近异动”更专业。

---

### P1-05：生日提醒不属于人事运营核心

生日可以存在于 HR17 教职工服务、文化关怀等场景，但不占 HR01 人事处控制台核心面积。

**裁决：从 HR01 主工作台删除。**

---

### P1-06：部门 / 岗位只看 Top N 会丢失语义

当前 Top12/Top10 如果不显示 Others 或总数，会让结构图看起来完整但实际上截断数据。

**裁决：所有 Top N 必须：**

- 显示 Others；
- 或显式标记 Top N；
- 可进入完整分析页。

# 5. HR01 信息架构冻结

HR01 保留 5 个三级工作区。

## HR01-01 人事总览

**一句话目标：** 人事处打开系统 10 秒内知道“人有多少、今天有什么事、最近有什么风险、队伍有什么变化”。

## HR01-02 我的待办

**一句话目标：** 把散落在招聘、入职、合同、异动、考核、职称等模块的“当前由我处理”的事项聚合到一个工作台，但不复制业务状态机。

## HR01-03 人事预警

**一句话目标：** 把“如果今天不处理，未来会形成管理事故”的事项按严重程度和截止日期排序。

## HR01-04 队伍结构

**一句话目标：** 回答“学校/学院教师队伍结构是否合理、哪里存在缺口、趋势是否恶化”。

## HR01-05 快捷办理

**一句话目标：** 让高频业务从首页 1 次点击进入真实办理入口，不让老师/人事管理员记菜单位置。

# 6. 角色模型

## 6.1 角色

### R1 学校人事管理员

- 全校人事业务；
- 可看绝大多数 HR01 明细；
- 敏感指标仍需专项权限。

### R2 人事处负责人

- 全校汇总；
- 风险；
- 待办监督；
- 结构分析；
- 允许下钻但敏感字段按权限控制。

### R3 二级学院人事秘书

- 本学院；
- 可看本学院人员、待办、风险；
- 不得看到其他学院。

### R4 二级学院负责人

- 本学院汇总；
- 本学院相关风险；
- 不默认查看个人敏感档案。

### R5 学校领导

- 全校高层汇总；
- 趋势和结构；
- 风险总量；
- 默认不展示不必要 PII。

### R6 普通教职工

- **不使用 HR01 管理工作台。**
- 进入 HR17 教职工服务中心。

### R7 SaaS 平台运营人员

- 只能看系统健康、租户启停、容量等平台数据；
- **不得因为是平台运营就默认读取学校人事事实。**

## 6.3 数据范围

统一使用：

```text
SCHOOL
COLLEGE
DEPARTMENT
ASSIGNED
```

规则：

- `SCHOOL`：当前学校全校；
- `COLLEGE`：一个或多个学院；
- `DEPARTMENT`：指定部门；
- `ASSIGNED`：只允许本人被分配处理的事项。

所有 KPI 与 drilldown 必须带同一个 `ResolvedHrScope`。

严禁：

> KPI 用全校数据，点进去后列表只剩本学院；

# 7. 统计上下文与“一个数字”的定义

HR01 所有指标必须返回同一类可信合同。一个数字不能只返回 `value`。

```json
{
  "metricKey": "active_headcount",
  "value": 1286,
  "status": "OK",
  "asOf": "2026-08-08",
  "period": {
    "from": "2026-01-01",
    "to": "2026-08-08"
  },
  "scope": {
    "type": "SCHOOL",
    "id": "school-001"
  },
  "definitionVersion": "1.0",
  "dataBasis": "AUTHORITATIVE_EFFECTIVE_FACT",
  "computedAt": "2026-08-08T14:20:12+08:00",
  "sourceUpdatedAt": "2026-08-08T14:19:45+08:00",
  "freshUntil": "2026-08-08T14:21:12+08:00",
  "maxStaleSeconds": 180,
  "staleReason": null,
  "drilldown": {
    "route": "/hr/staff",
    "contractVersion": "1"
  }
}
```

## 7.1 指标状态

### `OK`

完整、可信，且未超过该指标 `maxStaleSeconds`。

### `PARTIAL`

部分来源未接入或部分维度缺失；允许展示，但必须明确缺失来源。

### `UNAVAILABLE`

依赖模块未建设、未启用、当前数据基础无法提供该指标，或历史事实尚未具备。

### `STALE`

最近一次成功结果仍可解释，但已经超过该指标允许的新鲜度上限，或者权威来源已经出现比当前缓存更新的事实。

### `ERROR`

计算失败，且不满足安全的 stale-on-error 展示合同。

**`UNAVAILABLE / ERROR / STALE` 绝不能转成 0。**

## 7.2 同屏一致性合同

同一次 `/home/bootstrap` 返回的所有指标必须共享：

```text
tenantId
resolvedScopeFingerprint
asOf
period
schoolTimezone
requestSnapshotAt
```

同一 source domain 的指标优先批量查询，避免同一页面出现：

- 在岗教职工 1286；
- 学院分布合计 1281；
- 人员类别合计 1293；

却没有任何解释。

如果跨域来源在同一请求内无法保证严格快照一致，则 response root 必须报告：

```text
consistency = CONSISTENT / EVENTUALLY_CONSISTENT / PARTIAL
```

并允许 UI 显示“部分来源更新时间不同”。

## 7.3 时间边界

所有“今天、本月、本年、90 天内”等判断必须基于：

```text
HrRequestContext.school_timezone
```

禁止在领域 selector 中直接使用：

```python
date.today()
datetime.today()
```

除非其值已经明确转换到当前学校时区。

中国学校默认可配置为 `Asia/Shanghai`，但系统合同不能依赖服务器恰好也位于同一时区。

```python
    label="新增教职工",
    required_permissions=("hr.staff.create",),
    required_module="hr03",
    route_name="hr-staff-create",
    icon="user-plus",
    priority=10,
    audiences=("HR_ADMIN", "COLLEGE_HR_SECRETARY"),
    allowed_scope_types=("SCHOOL", "COLLEGE"),
    scope_validator="hr03.quick_actions.can_create_staff_in_scope",
    feature_flag="hr03.staff_create_enabled",
    availability_provider="hr03.quick_actions.staff_create_availability",
)
```

不要把快捷动作写死在 HTML。

### `allowed_scope_types`

解决静态范围约束。

例：

```text
staff.export_school_roster → SCHOOL
staff.create               → SCHOOL / COLLEGE
recruitment.plan.create    → SCHOOL / COLLEGE（取决于学校授权策略）
```

### `scope_validator`

解决仅靠 scope 类型无法表达的动态规则，例如：

- 当前学院是否属于该用户管理范围；
- 当前学院是否允许自行新增外聘教师；
- 当前学校是否要求新增正式教职工只能由人事处办理；
- 当前 scope 是否已经完成 HR02/HR03 数据切换。

**`scope_validator` 必须在后端执行。前端只能消费计算后的 Action Catalog，不能自己决定授权。**

### `availability_provider`

负责业务可用性，不负责授权。例如：

- 招聘模块未启用；
- 当前没有开放招聘年度；
- 系统处于迁移冻结窗口；
- 对应 workflow 未配置。

# 17. 指标注册表

V1 必须建立代码级 `MetricDefinitionRegistry`，但不做可视化 SQL 指标编辑器。

推荐定义：

```python
MetricDefinition(
    key="active_headcount",
    name="在岗教职工",
    definition_version="1.0",
    unit="person",
    owner_domain="hr03",
    source_domains=("hr03",),
    sensitivity="NORMAL",
    supported_scopes=("SCHOOL", "COLLEGE", "DEPARTMENT"),
    cache_ttl_seconds=60,
    max_stale_seconds=180,
    hard_expire_seconds=900,
    serve_stale_on_error=True,
    freshness_mode="EVENT_OR_TTL",
)
```

每个指标必须至少定义：

```text
key
中文名
业务定义
owner domain
source domains
计算方式
时间语义
可用维度
权限
敏感等级
definition version
cacheTtlSeconds
maxStaleSeconds
hardExpireSeconds
serveStaleOnError
freshnessMode
```

## 17.1 三个时间参数不能混为一谈

### `cacheTtlSeconds`

正常情况下缓存多久后应主动重算。

### `maxStaleSeconds`

超过多久以后，用户必须明确看到 `STALE`，即使系统为了降级仍临时展示最后一次成功值。

### `hardExpireSeconds`

超过该时间后，旧值不再允许作为正常页面数据继续服务；只能进入 `ERROR/UNAVAILABLE`，除非该指标经过单独风险批准。

**所以 TTL ≠ STALE 阈值 ≠ 最终不可服务阈值。**

## 17.2 `serveStaleOnError`

并非所有指标都允许失败时继续展示旧值。

例如：

- 人员结构分析：可短时间 stale-on-error；
- 普通 headcount：可短时间 stale-on-error，但必须标 STALE；
- 当前 CRITICAL 风险数量：默认不允许长时间用旧值冒充当前风险；
- 权限/租户相关指标：禁止 stale cache 越过权限变化继续服务。

## 17.3 Definition Version

指标公式发生语义变化时必须提高 `definition_version`。

缓存 key、导出、审计、API 响应必须携带该版本，避免“同名 KPI 在不同发布日期含义已经不同”却无法追溯。

# 18. 时间事实与业务日历

HR01 所有正式统计必须区分：

## `as_of`

某一天“当时是什么”。

## `period`

某一段时间“发生了什么”。

例如：

- 2026-08-08 在岗人数 → `as_of`；
- 2026 年新入职 → `period`；
- 过去 12 个月人数趋势 → 每月末 `as_of`。

这是整个 HR01 统计正确性的基础。

## 18.1 学校时区

所有时间边界由：

```text
school_timezone
```

决定。

API response root 返回：

```json
{
  "timezone": "Asia/Shanghai"
}
```

禁止浏览器时区、GitHub runner 时区或服务器 UTC 偶然决定业务日期。

## 18.2 年度口径

“本年新进/本年离退”默认使用自然年，但必须在 `MetricDefinition` 中显式声明：

```text
periodCalendar = CALENDAR_YEAR
```

如果学校未来要求学年/财政年度口径，新增枚举，不允许偷偷改变现有指标含义。

## 18.3 日界线测试

测试必须覆盖：

- 23:59 → 00:00；
- 月末；
- 年末；
- 闰年；
- 不同时区服务器环境下结果一致。

# 19. 缓存、实时性与数据新鲜度

这一节是 HR01 的生产可信度硬合同。

**缓存 TTL 只解决性能，不等于数据是否可信。**

每个 MetricDefinition 都必须独立定义 `maxStaleSeconds`。

## 19.1 数据新鲜度目标

V1 默认建议：

| 数据类型 | cache TTL | max stale | hard expire | 默认 stale-on-error |
|---|---:|---:|---:|---|
| 我的待办摘要 | 15s | 30s | 120s | 否 |
| CRITICAL/HIGH 预警摘要 | 15s | 30s | 120s | 否 |
| 首屏人数 KPI | 60s | 180s | 900s | 是 |
| 队伍结构 | 300s | 600s | 3600s | 是 |
| 历史趋势 | 1800s | 3600s | 21600s | 是 |
| Quick Action Catalog | 30s | 60s | 300s | 否 |

具体值可以按性能证据调整，但调整必须进入代码/配置评审，不能每个页面自行决定。

## 19.2 `STALE` 判定

指标满足任一条件即标记 `STALE`：

### 条件 A：最后一次成功计算超过阈值

```text
now - lastSuccessfulComputedAt > maxStaleSeconds
```

### 条件 B：权威来源已有更新，但当前结果还没重算

```text
sourceUpdatedAt > computedAt
```

### 条件 C：事件失效消息已经到达，但刷新尚未完成

```text
invalidationPending = true
```

### 条件 D：Provider 明确报告源数据落后

例如下游异步事实同步滞后。

## 19.3 UI 表达

`HrMetricCard` 在 STALE 时必须：

- 显示 `数据可能已过期` badge；
- 显示“数据更新于 14:20”；
- 可显示“最新变更可能尚未反映”；
- 保留最近成功值时，颜色不可与正常 `OK` 完全相同；
- 不能通过 loading skeleton 把 stale 状态遮掉；
- 不允许自动把 STALE 转成 `—`，除非已超过 hard expire。

示例：

```text
在岗教职工  1,286
数据可能已过期
更新于 14:20，最新变更可能尚未反映
```

## 19.4 Response Freshness Contract

每个 metric 至少返回：

```text
computedAt
sourceUpdatedAt
freshUntil
maxStaleSeconds
hardExpireAt
staleReason
cacheHit
```

Bootstrap root 另返回：

```text
freshnessSummary.okCount
freshnessSummary.staleCount
freshnessSummary.errorCount
freshnessSummary.oldestComputedAt
```

## 19.5 Cache Key

必须包含：

```text
tenant_id
user/permission fingerprint（按需要）
scope fingerprint
metric key
as_of
period
definition version
authority provider mode
```

不能只写：

```text
dashboard_total_employee
```

否则可能出现：

- 跨学校串数据；
- scope 变化还复用旧值；
- HR03 切换新 Provider 后仍命中 Legacy 缓存；
- 指标公式升级后命中旧版本缓存。

## 19.6 失效

优先：

> 正式事实变更 → domain event/outbox → invalidate → single-flight refresh

暂不具备事件机制时：

- 短 TTL；
- 写后针对 tenant/scope 显式 invalidate；
- 关键 HR02/HR03 写操作完成后必须发送缓存失效信号。

## 19.7 Cache Stampede 防护

高频首页不能在缓存同时过期时让几十个请求一起打数据库。

对重指标采用：

- Redis 分布式 lock / single-flight；
- 一个请求负责重算；
- 其他请求在允许范围内短暂读取旧值并标 STALE，或等待有限时间；
- 不允许无限阻塞；
- lock 必须有超时，避免死锁。

## 19.8 权限变化优先于缓存

缓存绝不能让已撤销权限继续生效。

涉及用户/角色/data scope 的结果：

- cache key 必须带 permission/scope fingerprint；
- membership/role/scope 变更后显式失效；
- 高敏感结果禁止使用不带用户授权上下文的共享缓存。

## 19.9 失败时的 stale serving

只有 `MetricDefinition.serveStaleOnError = True` 才允许展示最后一次成功值。

即使允许，也必须：

```text
status = STALE
staleReason = PROVIDER_ERROR
```

不能把旧值伪装成 `OK`。

## 30.2 迁移不得“猜历史”

Legacy 只有当前快照时：

- 可以迁移“当前组织”；
- 可以迁移“当前岗位”；
- 可以迁移“当前人员类别”；
- **不能反推出过去每年的组织/岗位/人员类别。**

如果学校能提供历史 Excel/旧数据库，再走专门历史导入。

否则：

```text
historicalCoverage = CURRENT_SNAPSHOT_ONLY
```

并在 HR01 历史指标中返回 `UNAVAILABLE`，直到有可信历史事实。

## 30.3 Legacy Provider 三阶段

### `LEGACY_ONLY`

HR02/HR03 尚未就绪。

允许 HR01 读取 Legacy current snapshot，但：

```text
dataBasis = LEGACY_CURRENT_SNAPSHOT
```

### `DUAL_READ_COMPARE`

新事实层已导入，但还在验真。

规则：

- 生产 UI 优先展示 authority 结果；
- 后台同时计算 legacy 结果用于对账；
- 差异进入 `AuthorityDiff` 监控/报告；
- 禁止把两个来源混合拼成一个数字；
- 关键差异未归零前不得切 authority-only。

建议比对：

```text
在岗人数
按学院人数
按人员类别人数
当前组织映射
当前岗位映射
未绑定人员
重复工号
跨租户错配
```

### `AUTHORITY_ONLY`

正式切换。

规则：

- HR01 只能读新权威 Provider；
- LegacyProvider 在生产路径被硬禁用；
- legacy cache namespace 立即失效；
- 旧 dashboard legacy API 不再作为业务数据源；
- 任意 legacy provider 生产调用触发监控告警。

## 30.4 切换开关

不要只用一个全局 boolean。

建议按 tenant/domain 存储：

```text
HrAuthorityCutover
- tenant_id
- domain                ORGANIZATION / STAFF
- mode                  LEGACY_ONLY / DUAL_READ_COMPARE / AUTHORITY_ONLY
- cutover_at
- cutover_by
- reason
- source_snapshot_hash
- mapping_version
- verification_report_id
```

原因：不同学校的数据迁移成熟时间可能不同。

## 30.5 切换前硬门

进入 `AUTHORITY_ONLY` 前至少满足：

- 当前在岗人员映射覆盖率 100%；
- active staff 未映射组织 = 0（允许的特例必须显式白名单）；
- tenant 错配 = 0；
- 重复工号/身份冲突 = 0；
- 当前学校 headcount 对账差异 = 0；
- 学院分布对账差异 = 0；
- 权限/data scope 回归全绿；
- 新 Provider 性能门通过；
- legacy 缓存已具备一键失效；
- 数据快照与 verification report 已归档。

## 30.6 紧急回滚

允许受控回滚，但必须：

- 仅授权系统迁移管理员；
- 强制 reason；
- 写审计；
- 明确回到 `DUAL_READ_COMPARE`，而不是静默 Legacy fallback；
- 回滚后首页显示“数据迁移验证中”的数据质量提示；
- 不允许应用异常时自动改 mode。

## 30.7 Legacy 下线完成定义

只有以下条件同时成立才可以删除 legacy adapter：

- 所有生产 tenant 进入 `AUTHORITY_ONLY`；
- 连续至少一个发布周期 legacy provider call = 0；
- 旧 API usage = 0；
- 相关 Horilla 模块已经完成 projection 兼容或重构；
- 删除前已有回归证据和数据快照。

# 31. 后端 API 详细合同与版本化策略

统一前缀：

```text

```

`v1` 是 **Major API Version**。

## 31.0 API Versioning 总合同

所有 `bootstrap` 和 `list` 接口 response root 必须包含：

```json
{
  "apiVersion": "1",
  "schemaVersion": "1.0",
  "generatedAt": "2026-08-08T19:20:00+08:00",
  "requestId": "..."
}
```

### V1 兼容原则

在 V1 稳定期：

**允许：**

- 增加新字段；
- 增加新枚举值（前端必须有 unknown fallback）；
- 增加可选对象；
- 增加新的 endpoint。

**禁止直接做：**

- 删除已有字段；
- 修改已有字段类型；
- 把可空改成前端无法兼容的强必填；
- 更改既有字段业务语义但保持同名；
- 改分页结构；
- 将 `OK/STALE/...` 状态含义偷偷重定义。

Breaking Change 必须：

- 开 `/api/hr/v2/`；
- 或保留旧字段并新增替代字段，进入明确 deprecated 过渡期。

### Deprecated Field

如确需替换：

```json
{
  "oldField": "...",
  "newField": "...",
  "meta": {
    "deprecatedFields": ["oldField"]
  }
}
```

不得通过 `newField_deprecatedOldField` 形成长期脏命名；过渡应有明确清理版本。

### 前端规则

- 必须校验 `apiVersion` major；
- 不识别 major 时进入可解释错误页，禁止继续猜字段；
- 对新增字段采用向前兼容；
- 对未知 enum 显示“未知状态”，不能 crash；
- UI 不能依赖 JSON 字段顺序。

# 32. HTTP 错误语义

统一：

```text
400 INVALID_REQUEST
401 UNAUTHENTICATED
403 PERMISSION_DENIED
403 TENANT_CONTEXT_REQUIRED
403 SCOPE_NOT_ALLOWED
404 RESOURCE_NOT_FOUND
409 VERSION_CONFLICT
409 AUTHORITY_CUTOVER_IN_PROGRESS
422 BUSINESS_RULE_VIOLATION
429 RATE_LIMITED
503 PROVIDER_UNAVAILABLE
503 AUTHORITY_SOURCE_UNAVAILABLE
```

原则：

- 越权不能靠 200 + empty list 模糊掉所有问题；
- 但为了防止对象枚举，具体详情接口可按安全策略返回 404；
- 所有 error envelope 带 `apiVersion/schemaVersion/requestId`；
- `AUTHORITY_ONLY` 时新 Provider 失败返回权威源异常，不能在错误处理器里切回 Legacy；
- 前端根据 error code 选择可解释状态，不根据英文 message 写业务判断。

# 39. 自纠错复核

在完成终极版后，再从“产品、数据、迁移、权限、架构、UI、施工可执行性”七个维度反查，形成以下修正。

## 修正 1：没有把 HR01 放在 HR02/HR03 之前强行生产

虽然文档编号是 HR01，但产品首页依赖权威事实。

因此：

- HR01 文档可以第一个完成；
- UI shell/provider contract 可以提前；
- **权威历史指标必须等待 HR02/HR03。**

## 修正 2：没有照搬 Horilla 当前 Headcount Trend

当前算法无法正确回答历史人员数量，已经明确禁止继续作为历史事实。

## 修正 3：没有把所有下游模块未建设值写成 0

改为标准：

```text
OK / PARTIAL / UNAVAILABLE / STALE / ERROR
```

## 修正 4：没有为了“顶级 UI”换前端框架

V1 保留 Django Template 架构，只提升结构、公共组件、API 和工程质量，继续利用 Horilla 捷径。

## 修正 5：没有把工作台做成第二审批中心

待办只是聚合入口，真实业务状态机仍归领域服务。

## 修正 6：没有让“美观”伤害效率

高级感来自：

- 数据结论清晰；
- 层级干净；
- 色彩克制；
- 状态真实；
- 可立即行动；
- 大量数据仍不乱。

## 修正 7：把 TTL 与数据新鲜度彻底分开

原版只定义了 60 秒、5 分钟等 TTL，还不足以告诉用户“什么时候数据已经不可信”。

终极版增加：

```text
cacheTtlSeconds
maxStaleSeconds
hardExpireSeconds
```

并把 STALE 变成正式业务状态。

## 修正 8：快捷办理从“permission 判断”升级为完整授权

新增：

```text
allowed_scope_types
scope_validator
availability_provider
```

避免学院用户看到全校动作后才 403。

## 修正 9：API 版本号不再只存在 URL 中

所有 bootstrap/list/error response root 都明确带：

```text
apiVersion
schemaVersion
requestId
```

V1 坚持 additive evolution。

## 修正 10：Legacy 不再是“以后记得替换”的软约定

建立：

```text
LEGACY_ONLY → DUAL_READ_COMPARE → AUTHORITY_ONLY
```

以及 tenant/domain 级切换记录、对账门和生产硬断点。

## 修正 11：没有让“自动 fallback”掩盖新事实层故障

进入 Authority-only 后，新 Provider 故障必须显式暴露，不能为了 KPI 好看再读旧 Employee 表。

## 修正 12：补上学校时区

当前 Horilla dashboard 使用 `date.today()` 类代码容易把服务器日期当业务日期。

终极版要求全部进入 `HrRequestContext.school_timezone`。

## 修正 13：补上同屏一致性

同一个 bootstrap 内 KPI、趋势、结构必须共享：

```text
asOf / period / tenant / scopeFingerprint / requestSnapshotAt
```

防止同一屏数字彼此打架。

## 修正 14：补上缓存击穿与权限失效

不仅要求缓存快，还要求：

- single-flight；
- 权限变更失效；
- authority mode 进入 cache key；
- legacy cache 在切换时清除。

这使 HR01 从“漂亮 Dashboard”升级为真正可长期运营的控制台。
