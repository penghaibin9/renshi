# V9 操作与业务约定

## 1. 录用：先核对真实内容，再审批

原“招聘 → 拟录用”工作台新增按候选人、申请号和岗位查找的历史分页；待形成拟录用和已形成拟录用分别分页。已经形成的申请不会因不在本页而再次列为可创建。

审批人员展开“查看已保存通知”读取通知编号、用工性质、预计报到、有效截止和版本；审批/签发弹窗再次展示这些保存值。已知用工类别显示中文；日期时间明确以北京时间呈现；完整内容指纹放入可展开记录。创建、审批、签发沿用各自原动作，不能一键跳完。

保存内容被其他人更改后，旧页面的审批/签发被拒绝；重新读取并核对后再办。通知指纹不是电子签章、不可篡改文档仓库或全部历史通知版本库，不能把这个保护夸大为完整电子合同能力。

## 2. 找人和分派：不再依赖手抄内部编号

待报到列表可按安全姓名摘要、工号/原查询字段定位同一入职单。姓名来自同校正式人员或预入职资料；同名者按工号/单号区分，未返回资料不在前端拼造。进入详情后用“材料”“协同”等原页面链接承接当前对象。

管理员在协同任务页查看待办、我的任务、待分派、逾期或已办。未分派任务不再投递给所有人的HR01个人待办。

“分派责任人”窗口输入至少两个字符的姓名或登录账号，点击查找、选择已有办理权限的本校有效账号，并说明分派/转派原因。选择本身不提交；最后确认才保存。查找有边界和截断提示，不承诺完整员工目录。分派不会自动给账号授予权限。

任务执行人使用auth User主键。旧数据的assignee_id如曾填入员工表ID或外部系统ID，必须先核对并按授权流程重新分派，不能猜测映射。

## 3. 责任人：完成的是有结果的事项

责任人只从本人的任务队列办理。页面显示必要的人员姓名/入职单、任务、责任岗位、前置事项、期限以及合法动作，不提供整份人员履历、银行卡或医疗资料。

先处理前置事项，再开始办理；确认完成需写实际结果与凭证依据。人工不能把自动开通类任务伪装成成功；自动任务继续等待原系统回执。管理员也不能冒充另一位指定责任人直接完成其任务。确有依据的豁免使用独立权限和原因，不能拿完成代替豁免。

每次提交携带当时的版本及幂等编号。别人已经更新，旧版本会被拒绝。网络结果不明时，当前窗口保留原内容、原编号，仅供明确“核对原提交”；不自动重复写入，也不更换编号盲目重发。关闭/刷新后不保证草稿恢复，应先读取服务器最新状态。

## 4. 材料：交一份，不丢另一份

从人员列表直接进入材料页；原定位编号输入仍保留为兼容入口，可粘贴定位，但正常办理不要求人事老师记住UUID。

读取不自动创建材料记录。原模板要求有缺失实例时，授权人员明确点击生成，再办理。

上传一项，只更新当前行，其余行选中的File节点与文件选择继续保留在本页。上传不等于核验通过。核验、退回、豁免分别填写实际依据/原因；已核验/豁免及核验中材料不允许直接重新上传覆盖。下载保留原授权票据和审计链。完整材料历史版本库不属于本轮新增范围。

切换入职单或重新读取会检查未提交文件；取消切换后恢复原定位值和文件选择。提交结果不明时保持本行锁定与原文件/编号，明确核对同一提交；不能替换成另一份文件继续用同一编号。

## 5. 人事复核：核对业务结果，而非看任务数量

“结果核对”以原正式四层记录和生效事实链为依据，分别显示：

- 自然人、本校教职工、用工、任职是否形成一致的正式事实；
- 原模板必需事项和材料是否达到原完成政策；
- 是否有未解决冲突、过期材料或根本没有生成的模板任务；
- 后续尚未完成及影响起薪的任务。

确认结案绑定本次核对的内容指纹与版本。来源变化须重读，不拿旧页面结果继续关闭。结案使用原ACTIVE→ONBOARDING_IN_PROGRESS→ONBOARDING_COMPLETED合法转换。试用等原状态不强行改写；未被原状态机支持的结案阶段会明确阻断，不能理解为全部试用场景都已完成改造。

非阻塞后续任务仍保留原责任和状态，不为了显示“完成”批量打勾。结案不会自动起薪、发款、生成工资或结束试用；存在起薪事项仍走原工资检查。

办理事实、审计回执和幂等记录放在同一服务事务里；OnboardingCompleted写入原事件待发箱。待发箱记录不代表外部部门、消息平台或HR15已经成功消费。

## 6. 前端连续性范围

当前页面内存保留未提交说明/文件；取消、失败和读取失败不冒充成功。不持久化人员或文件草稿到localStorage/sessionStorage；刷新、退出或浏览器崩溃后不保证恢复。服务器的版本/幂等防线是独立保护，不等同浏览器草稿保存。
