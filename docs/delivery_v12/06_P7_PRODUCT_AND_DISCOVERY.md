# P7｜对外产品介绍与需求访谈稿

## 产品定位

**跃科高校人事管理与教师发展系统**

首单聚焦：人员主档、材料核验与新教师入职协同。让同一名教师的资料、责任任务和正式结果能关联起来，减少按名单反复收表、抄编号和口头催办。原HR01–HR18仍保留，其他模块按范围逐项验证和报价。

## 可以展示什么

人事办理员找同一名教师→查看缺口→选择独立发布的学校方案→连续上传材料→责任部门有据完成任务→人事核验→核对正式人员/用工/任职→协同结案。展示未完成和被拒绝的状态，不只展示一路成功。

已有的工资制度、标准、试算和补差能力可以单独介绍其限定范围；未进行学校实账、银行/税务联调前，不承诺立即替换学校现有发薪系统。

## 推荐的首次沟通话术

“我们先不请学校替换所有系统。请您选一件现在最费时间的人事事项，使用您授权的脱敏样本，把找人、收材料、部门接续、核对结果完整走一遍。确认范围和验收结果后，再决定是否试点和扩展。”

不能说：全部业务零风险；任意制度自动适配；全天候无限定制；自动对接所有校园系统；已经有未授权的学校案例；百分百原创独占全部代码。

## 访谈问题及应形成的记录

| 主题 | 问题 | 输出 |
|---|---|---|
| 业务痛点 | 最费时间的是找数据、重复填表、催部门还是核对结果？最近一次怎么处理？ | 一条真实任务及现状步骤，不杜撰效率百分比 |
| 对象与规模 | 校区/学院/人员类型、同名情况、每期入职/导入量？ | 约定的规模和边界 |
| 原系统 | 哪些系统继续保留？哪些环节无系统或不好用？ | 替换/补充清单 |
| 部门职责 | 谁发起、谁核验、谁发布、谁有最终决定权？ | 角色与范围矩阵 |
| 制度差异 | 清单、前置任务、生效日、试用与例外规定是什么？ | 经学校确认的方案要求 |
| 资料 | 是否能提供合法授权脱敏样本和字段说明？ | 授权用途、范围、保留/退出约定 |
| 接口 | SSO/财务/一卡通/邮件由谁授权？是否有真实文档和测试环境？ | 每个接口单独定范围、验收回执 |
| 运行 | 机房/云、MySQL版本、备份、证书、登录要求是什么？ | P2环境核对单 |
| 验收 | 谁愿意用真实角色复做？成功的判定是什么？ | 可执行的验收场景 |
| 采购与服务 | 校方采购路径、服务期、现场支持和预算边界？ | 下一步责任人与条件，不假定可直接签约 |

## 售前演示顺序

先说明使用的是受控环境还是正式环境。只展示上述一条业务链，演示一个权限拒绝、一个材料退回、一次重复请求核对和一份迁入台账。最后明确已实现/待配置/待开发/待联调/待学校验收五类，不用一个“都支持”回答所有问题。

需记录一次任务的页面切换、重复选择、输入重填和遇到的阻塞；有真实前后测量后才能陈述效率提升。不自动把客户姓名、校徽、截图用于宣传。
