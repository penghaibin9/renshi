# P6｜发布、运维、售后与退场

## 发布原则

V12无新增业务表和数据库迁移，但有后端、API、页面与工具变更。必须同步部署对应前后端；从更早版本升级仍执行原历史迁移，不因本轮没有新迁移就跳过V8/V10。先比较并行改动，不整包覆盖另一个施工窗口。

发布记录：批准人；当前/目标版本；代码和包哈希；当前迁移头；备份位置与校验；停写范围和worker处理；已知问题；静态资源/缓存更新；主链验证；是否允许开放用户；回退负责人。

使用原 `docker-compose.prod.yml` 的 release/prepare_runtime 过程。先在全新独立验收项目运行 `python scripts/run_hr_p012_gate.py --report <全新JSON路径>`；此命令默认只诊断。`--execute` 会创建隔离验收项目，必须由操作者确认本机资源，不连接生产或远程Docker。技术检测通过仍不是客户验收。

不要把未经生产配置核验的测试 settings 放进正式镜像。不能关闭学校权限、MFA、CSRF、上传扫描或迁移保护来消除错误。当前缺 environ/Docker/MySQL 的宿主不是部署成功环境。

## 回退不是把ZIP解回去

已产生新正式记录、模板绑定、回执或工资事实时，先停止新增写入，核对进行中任务与回执，优先前向修复。回滚页面/工具不应删除事实。恢复数据库会影响备份之后的全部数据，必须有单独批准和增量处置，不是“撤销某一教师”。

## 故障分级与真实可承诺服务

| 级别 | 例子 | 即刻处理动作 | 响应/恢复目标 |
|---|---|---|---|
| 紧急 | 越权泄露、错误生效、工资错误、恢复风险 | 停止相关写入/暴露入口，保全证据，通知指定负责人 | 合同填写，未确认不承诺全天即时修复 |
| 高 | 核心主链无法继续、导入不可恢复、所有人无法登录 | 记录对象/请求/版本，限定影响，核对备份 | 双方确认 |
| 中 | 单一操作受影响但有安全替代流程 | 登记复现与影响，安排受控修复 | 双方确认 |
| 低 | 文字、样式、非阻塞便利性 | 合并到维护计划 | 双方确认 |

工单仅记录必要信息：学校代号、时间、模块、对象内部编号、请求编号、版本、错误代码、影响人数、复现步骤、已采取动作、联系人、状态。不要贴身份证、银行卡、完整工资表或生产密码到普通聊天/邮件。

## 持续运维的责任表

学校指定：账号授权和离职停用、制度与材料清单批准、数据合法性、业务核验、验收签认。跃科或实施伙伴按合同负责：范围内安装升级、故障定位、备份演练支持和培训。主机、证书、短信、邮件、外部接口和第三方费用逐项确定，不能默认由任一方无限承担。

备份周期、保存地、保留时长、可接受数据损失窗口和恢复目标由学校与运维共同确认。本包不预设符合所有学校的固定数值，不把“有脚本”当成备份可用。

## 退出与许可

交接时明确当前数据库范围、材料、原始标准、接口映射、账号停用、密钥轮换、保管人、校验清单和销毁约定。原开放交付命令可能包含全配置数据库，学校共库情况下不得直接单校外发。

保留原LICENSE、NOTICE、第三方组件和修改说明。根许可核对不等于全组件法律审计，不承诺第三方底座为跃科独占原创。对分发/源码义务和合同知识产权条款，由授权法律专业人员结合真实依赖关系复核。
