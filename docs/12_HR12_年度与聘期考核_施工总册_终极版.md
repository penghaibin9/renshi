# 0. 六个三级模块冻结
```text
HR12 年度与聘期考核
├─ HR12-01 考核制度与指标体系
├─ HR12-02 目标任务与平时考核
├─ HR12-03 年度考核
├─ HR12-04 聘期考核
├─ HR12-05 师德与专项考核
└─ HR12-06 评议审定与考核档案
```

六个工作区职责严格分离：

- **HR12-01 考核制度与指标体系**：考核类型、适用对象、岗位分类、指标库、评分/档次、权重、硬门槛、优秀比例政策、工作流、证据要求和版本发布。

- **HR12-03 年度考核**：年度批次、人员范围、个人总结、测评/核实/评价、组织评议、优秀候选、公示、集体审定、结果告知。

- **HR12-06 评议审定与考核档案**：校准、评议、集体审定、结果版本、书面告知、本人意见、异议/复核、更正、档案、结果应用追踪和统计。

# 1. 结论先行
HR12 不是“给老师打一个 1~5 分”，也不是把 Horilla 的 OKR 直接换成中文。

它是高校人员 **Assessment Authority**：

```text
HR03 Person / Employment / Assignment
                 │
                 ▼
       Assessment Eligibility
                 │
                 ▼
       PolicyVersion + Cycle
                 │
      ┌──────────┼────────────┐
      ▼          ▼            ▼
  Goals/Tasks  Evidence     Gate Facts
      │          │            │
      └──────────┼────────────┘
                 ▼
          Assessment Case
                 │
   ┌─────────────┼──────────────────┐
   ▼             ▼                  ▼
Self Review   Reviewer Eval     Multi-source Facts
   │             │                  │
   └─────────────┼──────────────────┘
                 ▼
       Verification / Analysis
                 │
                 ▼
       Calibration / Deliberation
                 │
                 ▼
        Collective Finalization
                 │
                 ▼
       Final Assessment Result
```

HR12 必须回答“为什么是这个结果”，而不是只保存最终档次。

# 2. HR12 必须回答的生产问题
至少必须回答：

1. 这个人为什么进入本次考核，依据哪个人员/岗位/聘期事实？
2. 他适用哪套考核制度、哪个版本、哪种岗位分类？
3. 教师、辅导员、管理岗、实验技术、工勤、外聘人员是否采用不同模板？
4. 年度考核按自然年还是学校学年，谁配置？
5. 聘期考核范围来自哪个 HR07 Contract/Term？
6. 考核指标的定义、权重、评分尺度当时是什么？
7. 哪些指标是量化参考，哪些必须人工评价？
8. 哪些条件是硬门槛，不能被总分抵消？
9. 师德问题是否来自正式事实，而不是舆情/AI 猜测？
10. 教学工作量、质量、成果来自哪个教务事实？
11. 科研成果如何避免重复计数、挂名计数和当前数据污染历史？
12. HR10 培训/企业实践只读哪些 VERIFIED facts？
13. HR11 考勤数据是否来自已月结/冻结指标？
14. 目标在年度中途变化如何留版本和审批？
15. 自评内容能否直接成为正式事实？
16. 同一成果被多个目标引用是否重复得分？
17. 360 评价是否匿名、谁能看原始回答？
18. 评价人是否存在利益冲突/回避问题？
19. 校准前后的分数为什么变化？
20. 优秀人数控制是制度约束还是强制“正态分布”？
21. 谁具有最终确定档次的权限？
22. 拟优秀结果是否需要公示，公示过程如何留痕？
23. 结果如何书面告知并记录本人意见？
24. 本人不同意结果如何提出异议/复核？
25. 已 FINALIZED 的结果是否还能直接 UPDATE？
26. 更正是业务重评还是纯数据纠错？
27. 聘期结果如何回给 HR07，而不是 HR12 直接续聘？
28. 年度结果如何给 HR13/HR14/HR15 使用而不被反向修改？
29. Provider 不可用时是否明确 `UNAVAILABLE`，而不是按 0 分？
30. 今天修改考核制度是否保持往年正式结果完全可解释？

# 3. 生产级红线
禁止：

- `Employee.performance_score = 92` 作为唯一考核真相；
- 一个通用 OKR 表承担年度、聘期、师德、专项全部语义；
- 只保存总分，不保存政策、指标、证据、评价、审定过程；
- 目标发布后原地修改并影响历史；
- 直接使用当前部门/岗位给往年考核分组；
- 把考勤异常数直接等同“勤”分数或纪律结论；
- 把教学评价均分直接等同教师年度考核档次；
- 把论文数、项目数、经费数机械折算为最终结论；
- 把培训学时/企业实践天数直接当“优秀”依据；
- 把师德作为普通 10% 权重，严重问题仍可被其他高分抵消；
- AI 自动给教师打分、排名、判定师德失范或建议辞退；
- 强制全校所有岗位一套指标、一套权重；
- 直接把企业 OKR “完成率”当事业单位年度考核；
- 强制正态分布或无制度依据强制末位淘汰；
- 为满足优秀比例偷偷改个人评分；
- 校准后不保留 before/after/reason/actor；
- FINALIZED 结果直接 UPDATE；
- Excel 直接导入 FINALIZED 结果；
- Provider 失败时自动 fallback 旧 PMS 并冒充权威；
- 未完成迁移/权限/并发/E2E 就切 HR12 Authority；
- 施工阶段直接合并 `main` 或部署生产。

# 4. 国家制度总框架
事业单位工作人员考核的产品基线必须支持：

```text
年度考核 ANNUAL
聘期考核 TERM
平时考核 ROUTINE
专项考核 SPECIAL
```

系统实现采用：

```text
National Baseline
      ↓
Province / Department Rule Pack
      ↓
School Assessment Policy
      ↓
Policy Version
      ↓
Cycle Frozen Snapshot
      ↓
Assessment Case
      ↓
Immutable Final Result
```

S0 施工必须核验目标省、主管部门、学校当年实际制度，不能把本文当法律意见。
---
# 5. 事业单位考核内容模型
考核内容至少能表达：

```text
德 MORALITY / CONDUCT
能 CAPABILITY
勤 DILIGENCE
绩 PERFORMANCE
廉 INTEGRITY
```

但高校实现不应只做五个固定文本框。

每个维度可以绑定：
- 岗位分类指标；
- 权威事实；
- qualitative review；
- hard gate；
- evidence requirement；
- result rule。

不同岗位的具体内容通过 PolicyVersion 配置。
---
# 6. 年度考核硬边界
年度考核是对一个年度/学校规定考核周期内表现的正式总评。

默认支持：

```text
EXCELLENT
QUALIFIED
BASICALLY_QUALIFIED
UNQUALIFIED
NO_RATING
```

注意：

- `NO_RATING` 不是 `UNQUALIFIED`；
- “不参加考核”“不确定档次”等特殊语义必须有 reason code；
- 优秀比例政策可配置并有制度来源；
- 比例约束不得通过暗改个人分数实现；
- 结果必须经正式审定，不由加权公式自动 FINALIZE。
---
# 7. 年度优秀比例硬边界
系统必须具备 `ExcellentQuotaPolicy`。

当前国家事业单位考核基线存在优秀人数比例管理要求，但实际适用范围、比例调整、分类倾斜必须由目标学校制度核验。

模型不得写死：

```text
excellent = top 20% by score
```

正确行为：

```text
calculate quota context
→ detect proposed over-quota
→ block/require authorized deliberation
→ preserve individual decision reasons
```

不能把 quota 做成“自动降档算法”。
---
# 8. 聘期考核硬边界
聘期考核必须直接引用 HR07 的完整聘期：

```text
agreement_id
term_id
term_start
term_end
position/duty snapshot
term_goal_snapshot
```

并汇总：

```text
annual assessment results within term
term goals
verified performance evidence
routine/special assessment references
formal gate facts
```

正式结果核心：

```text
QUALIFIED
UNQUALIFIED
NO_RATING / SPECIAL_POLICY
```

HR12 只输出考核结论；是否续聘、变更、不续聘由 HR07/HR16 继续处理。
---
# 9. 平时考核硬边界
平时考核用于日常工作和一贯表现的经常性评价。

可吸收成熟 HCM 的：

- goal check-in；
- continuous feedback；
- 阶段任务；
- 工作纪实；
- 主管谈话记录；
- 阶段性量化指标；
- 风险与改进计划。

但：

```text
RoutineFact / CheckIn / Feedback
      ↓ reference
Annual Assessment
```

平时记录不是正式年度档次。
---
# 10. 专项考核硬边界
专项考核用于重大项目、重点任务、专项行动、特定事件或学校明确的专项评价。

模型必须有：

```text
special_assessment_type
scope
task/event reference
target snapshot
evidence requirements
reviewers
result schema
effective period
```

专项结果可以成为年度/聘期重要参考，但不能绕过正式年度/聘期程序直接改档次。

# 12. 分类来源与历史
岗位分类来源必须引用 HR03/HR02 有效任职事实。

```text
staff + as_of
→ assignment / position / job family
→ ClassificationProfileVersion
```

禁止：

- 前端手选“我是教学科研型”就成为正式分类；
- 今日调岗导致去年考核模板变化；
- 多 Assignment 人员只取第一条而不校验。

多角色冲突由 Eligibility Resolver 显式处理。

# 13. 师德师风第一标准
师德必须作为独立治理维度，而不是普通加权题。

推荐：

```text
EthicsAssessmentGate
- status PASS / REVIEW_REQUIRED / BLOCKED_BY_FORMAL_FACT / UNAVAILABLE
- source_refs[]
- policy_version_id
- decided_by
- decided_at
- reason_code
```

关键：

- 可组织周期性师德自评/单位评价；
- 正式失范调查、处分、纪法处理不能由 HR12 黑箱替代；
- 已生效正式结论通过 Provider 引用；
- 制度规定“一票否决”时以 `HARD_GATE` 表达；
- 未核实投诉/舆情/AI 不得自动 BLOCKED。
---
# 14. 师德失范处理与考核边界
系统需要区分：

```text
ethics questionnaire
ethics periodic assessment
ethics complaint
formal investigation
formal decision
assessment gate effect
```

HR12 只负责考核相关的评价/引用。

未决投诉：

```text
PENDING_FORMAL_REVIEW
```

由 Policy 决定暂缓或人工审定，不允许评价人顺手把投诉改成“已查实”。

# 15. 评价改革对产品的约束
产品要支持：

```text
结果评价
过程评价
发展性参考
综合评价
分类评价
代表性成果
长周期评价
同行/多主体评价（按适用场景）
```

必须避免：

- 唯论文；
- 唯项目；
- 唯经费；
- 唯奖项；
- 唯数字；
- 单一学生评分代替综合教学评价；
- 同一硬指标评价所有学科/岗位。

量化数据是 `Evidence / MetricSnapshot`，不是 `FinalDecision`。

# 17. 公式得分与正式结论分离
任何自动计算只输出：

```text
calculated_score
calculated_level
calculated_recommendation
calculation_trace
```

正式结果：

```text
final_grade
decision_reason
decision_authority
```

两者是不同字段、不同权限、不同生命周期。

禁止：

```python
result.final_grade = calculate_score().grade
result.status = "FINALIZED"
```

# 18. Hard Gate 与 Score 分离
典型 Gate：

- 师德正式门槛；
- 必须完成的聘期目标；
- 正式纪律/合规事实；
- 学校制度明确的资格前置。

必须是 `GateEvaluation[]`。

总分 95 但 Gate 未决时：

```text
Score: 95
Final: BLOCKED / REVIEW_REQUIRED
```

不能用高分掩盖硬门槛，也不能用 Gate 替代有权组织审定。

# 24. Horilla 2.0 PMS 当前基线

```text

```

已具备目标、关键结果、进度、360、问卷、周期、反馈对象、meeting 等基础。

但大量直接绑定 Horilla `Employee / Company / Department / JobPosition`，且偏企业 OKR/feedback，不足以成为高校正式考核 Authority。
---
# 25. Horilla PMS 关键结构风险
S0 必须特别复审：

- `Period.period_name` 的范围/唯一性；
- Objective 与 Employee 直接绑定；
- EmployeeObjective 当前状态/进度语义；
- KeyResult target/current/progress 可信度；
- Feedback manager/colleague/subordinate/others；
- QuestionTemplate/Question 历史版本；
- AnonymousFeedback 的租户/权限边界；
- BonusPoint 与绩效之间的潜在耦合；
- scheduler 周期反馈；
- pms signals 的副作用；
- dashboard 统计来源。

不得凭“已有 PMS”判断 HR12 已完成 70%。
---
# 26. KEEP / ADAPT / REWRITE
## KEEP

- PMS 通用列表/筛选/分页；
- 目标进度交互；
- 360 feedback 交互；
- Question Template 基础；
- notification；
- generic forms；
- audit 技术能力；
- dashboard 部分布局。

## ADAPT

- Objective → Goal；
- KeyResult → GoalMeasure；
- EmployeeObjective → GoalAssignment；
- Feedback → Reviewer/MultiRater；
- Period → AssessmentCycle；
- existing employee selectors → HR03 Staff Provider。

## REWRITE

正式 Policy、年度/聘期/师德/专项、证据快照、审定、Result、异议、更正、档案和下游应用。
