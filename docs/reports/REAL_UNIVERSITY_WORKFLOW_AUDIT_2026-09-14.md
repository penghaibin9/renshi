# 高校人事系统真实业务链源码审计与第一轮整改报告

- 审计日期：2026-09-14
- 审计对象：当前上传的高校人事系统完整源码包
- 审计目标：按真实高校/事业单位人事场景检查“缺功能、假功能、半真流程、跨模块断链、关键政策口径错误”，并直接修改源码
- 主链范围：组织机构 → 教职工主档 → 招聘入职 → 异动合同 → 考核职称聘任 → 薪酬离退 → 教职工自助 → 数据中心
- 本轮结论：系统主体不是空壳，HR02～HR18 已具备较完整的权威数据模型、版本/留痕、权限和跨模块业务基础；本轮发现并修复 4 类高价值问题，另保留少量必须在真实运行环境继续验收的 P1 项。

> 注意：本报告中的“通过/已修复”仅指本轮能够在当前沙箱完成的源码级检查和静态验证。当前沙箱未安装 Django/MySQL 运行依赖，因此没有把历史的“3200 项测试通过”冒充为本次修改后的重新回归结果。

## 一、审计方法

本轮不是只看菜单和页面，而是逐条检查以下证据：

1. Django 模型、迁移、Service、Selector、API、URL 与页面动作是否一致。
2. 页面按钮是否真正落入权威业务事实，而不是只弹“成功”。
3. 跨模块是否引用真实主档、合同、聘期、考核结果等权威记录。
4. 外部系统未接通时是否 fail-closed，而不是伪造成功状态。
5. 高校/事业单位关键业务口径是否与国家现行规则一致。
6. 测试是否只靠测试自己插入数据才能“看起来有功能”。
7. 新学校干净数据库部署后是否仍能正常看到应有入口。
8. 关键评审材料、退休结论等是否存在可被管理员手填绕过权威事实的问题。

## 三、本轮已直接修改的关键问题

### 1. HR12 年度考核档次修正为四档

原问题：默认年度考核制度只有“优秀 / 合格 / 不合格”，漏掉“基本合格”。

已整改：

- 年度考核默认档次调整为：`EXCELLENT / QUALIFIED / BASIC_QUALIFIED / UNQUALIFIED`。
- 增加“基本合格”阈值配置及阈值顺序校验。
- 年度优秀比例规则只绑定年度考核。
- 前端制度创建页面同步展示四档，不再把三档错误固化到新制度。

政策依据：

- 《事业单位工作人员考核规定》：年度考核结果一般分为优秀、合格、基本合格、不合格四个档次。
- 《事业单位人事管理条例》第二十一条亦明确年度考核可分上述四档。

### 2. HR12 聘期考核从“半真功能”补成正式业务链

原问题：

- 有聘期考核菜单、模型和测试样例，但正式 API 没有从真实聘期创建 Case 的业务入口。
- 后台评议人员分配、最终审定候选仍只筛年度考核。
- 结果更正存在把年度“优秀”等档次错误写入聘期结果的风险。
- 页面曾把“年度考核 / 聘期考核 / 师德考核”画成类似顺序步骤，业务语义误导。

已整改：

- 聘期制度默认结果档次改为 `QUALIFIED / UNQUALIFIED` 两档。
- 聘期制度不创建年度“优秀比例”政策。
- 新增正式聘期 Case 创建入口，并强制引用：
  - HR14 正式聘期；
  - HR03 教职工主档；
  - HR07 有效聘用合同。
- 缺任一权威事实即阻断，不允许管理员手填一条“假聘期”继续办理。
- 聘期 Case 可继续进入：证据锁定 → 评议人员分配 → 集体审定 → 正式结果。
- 年度结果引用限定在聘期开始/结束年份范围内。
- 后台评议与最终审定候选同时识别 ANNUAL / TERM。
- 结果更正服务按考核类型限制可用档次：聘期不能改成“优秀/基本合格”等年度专属档次。
- 修正页面流程说明，将年度、聘期、师德按独立业务呈现。

政策依据：

- 《事业单位工作人员考核规定》第十八至二十一条：聘期考核以聘用（任）合同为依据、以聘期内年度考核结果为基础，结果一般为合格和不合格。

### 3. HR13 职称评审材料增加“不可操作性删除”保护

原问题：

- 已验收材料虽然实例保存受到限制，但 ORM QuerySet 仍可能批量更新/删除。
- 数据库层缺少针对职称评审材料的删除阻断。

已整改：

- 为 `TitleMaterialSnapshot` 增加专用 QuerySet：阻断批量 `update / bulk_update / delete`。
- 实例 `delete()` 明确禁止。
- 新增 MySQL `BEFORE DELETE` 触发器 `hr13_title_material_no_delete`。
- 增加服务层和迁移层回归测试源码。

政策依据：

- 教育部、人力资源社会保障部《高校教师职称评审监管暂行办法》第八条：高校职称评审过程有关材料档案应妥善留存至少 10 年，并保证评审全程可追溯。

本次采取比“10 年后允许普通删除”更保守的策略：业务模型内永久禁止直接删，未来如学校确需做达到保管年限后的档案处置，应另建受治理的归档/销毁流程，而不是恢复普通 delete。

### 4. HR16 正式退休事实不再允许脱离预审手填权威日期

原问题：

系统已经有退休预审引擎，可计算渐进式法定退休年龄；但正式形成退休事实时，管理员仍可直接提交 `retirementType/statutoryDate`，导致“预审算对，正式事实手填错”成为可能。

已整改：

- 正式退休事实必须提交 `precheckId`。
- 预审必须属于当前学校，且结论为 `ELIGIBLE`。
- 预审人与 ExitFact 人员、人事关系必须一致。
- 正式离职日期必须与预审冻结的法定退休日期一致。
- 退休类型与法定退休日期从预审权威结果派生，不再由页面自由决定。
- 兼容旧客户端传入字段时，只允许与预审权威值完全一致，否则冲突阻断。
- 前端正式办理入口只列出可匹配的“退休事实 + 合格预审”组合。

仍未冒充支持的边界：

- 2025 年起的弹性提前退休/弹性延迟退休，需要本人书面选择、单位协商/审批、通知时限、最长 3 年限制等独立证据链；本轮没有用一个字符串字段假装“已经完整支持”。
- 在单独建成上述证据与审批流程前，系统继续以法定退休预审为正式退休事实的权威来源。

政策依据：

- 《实施弹性退休制度暂行办法》：弹性提前退休最长提前 3 年且至少提前 3 个月书面告知单位；弹性延迟退休最长 3 年，单位与职工需提前 1 个月书面明确；国有企事业单位有关领导人员和其他管理人员还受相应程序约束。

### 5. HR17 干净学校不再出现“服务大厅空白”

原问题：

- HR17 服务目录模型、搜索、收藏、路由和数据 Provider 都存在。
- 但生产代码没有任何默认服务目录初始化逻辑；测试能看到目录主要因为测试自己插入了目录数据。
- 新学校干净建库后可能出现服务入口 0 条，属于典型“测试环境有、客户环境空”。

已整改：

- 新增幂等 `ensure_default_catalog_if_empty()`。
- 仅当学校一条服务配置都没有时创建 10 个默认本人入口，覆盖 HR03/04/05/06/07/12/13/14/15/16。
- 学校只要已有任何自定义目录（包括停用项），绝不混入或覆盖默认配置。
- 默认项全部采用“查看……”表述，只跳到各权威模块，不在 HR17 复制第二套业务状态机。
- 页面“我的档案与更正 / 我的申请与办理 / 我可以办理的服务”等容易夸大的文案改为“档案材料 / 待办与进度 / 服务入口”等真实能力描述。

## 四、没有被误判成“假功能”的重要能力

### HR15 薪酬外部支付

代码中已存在外部提供方未配置、调用失败或超时时的失败关闭逻辑；本轮未发现“银行没接却显示发放成功”的明显假实现。因此没有为了追求改动数量而重写 HR15。

### HR18 数据中心

数据源门禁明确保留 `UNAVAILABLE / ERROR`，证据哈希和质量信息存在。历史求值器目前能力声明本身就限定为 HR03 Count 级别，不会把“不支持的跨域指标”静默算成 0。本轮将它列为扩展能力，而不是定性为假数据。

## 五、当前仍应继续做的 P1

本轮源码级检查未发现还需要立即靠“手填假成功”才能跑主链的已知 P0，但正式上线前仍有以下 P1，建议按顺序继续：

1. **HR16 弹性退休完整证据流**：本人申请/书面告知、提前 3 个月、延迟协商和提前 1 个月书面约定、最长 3 年、干部人事审批权限、社保办理材料。
2. **HR17 真正 SELF 写操作**：教职工本人发起档案更正、本人材料补交等，应使用 SELF-safe API，由登录身份反查本人，不接受前端随意传 staff_id。
3. **HR18 多域历史指标**：在保留来源门禁/证据链的前提下，从 HR03 COUNT 扩展到招聘、入职、异动、合同、考核、职称、聘任、薪酬、离退等历史事实指标。
4. **真实外部适配器上线验收**：银行/财税/IAM/电子签章等必须在目标学校真实配置后单独验收；不能把本地 mock/未配置状态当生产完成。
5. **浏览器四角色 E2E**：学校人事管理员、二级单位负责人、普通教职工、审定/评委角色分别跑真实点击、权限越权、跨租户隔离和回退场景。
6. **生产数据库/备份/恢复/性能门禁**：在 MySQL/Redis/任务队列真实环境跑全量测试、迁移、回滚、备份恢复和大数据量查询性能。

## 六、P2 优化方向

- 学校级制度模板：不同高校可配置本校考核、聘期、岗位、职称方案，但必须版本冻结、留痕并受权限控制。
- 职称档案长期处置：未来如做超过法定/校内保存期后的销毁，应建立审批、清单、双人复核和销毁审计，不恢复普通 delete。
- HR17 移动端高频事项进一步收口，重点做“本人提交 + 审批进度 + 补件 + 结果查看”，不要把所有后台管理页搬到手机。
- 数据中心增加“指标口径版本 + 来源快照 + 重算批次 + 对账差异”可视化。
