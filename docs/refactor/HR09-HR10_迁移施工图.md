## 1. 目录归属

| 模块 | 新 Authority 目录 | 旧能力来源 | 裁决 |
|---|---|---|---|
| HR09 教师资格与双师型 | `hr_qualification/` | Horilla qualification/document/profile 相关事实仅作基线/证据来源 | **NEW**：教师资格、双师规则版本、申报、评审、复核/到期/撤销成为独立 Authority |
| HR10 培训进修与企业实践 | `hr10_development/` | Horilla employee/profile/documents/workflow/notification 仅作技术与迁移基线 | **NEW**：发展计划、培训、企业实践、过程证据、评价、成果和发展档案独立建模 |

## 2. 小白目录规则

HR09/HR10 新业务只进入自己的 `models.py`、`services/`、`selectors/`、`providers/`、`api/`、`tests/`、`README.md`。旧 profile/document/workflow 可以通过 adapter/provider 复用，但不得变成新的正式 Authority。

## 3. 搬迁顺序

1. HR09 先盘点已有 qualification/document/profile 字段与附件，区分“教师资格事实、职业资格/技能等级、双师认定、职称、荣誉称号”，禁止混成一个标签。
2. HR09 建规则版本、批次、申报证据包、预检、人工评审、结果和有效期历史；证据只能引用 HR03/HR10/教务等已核验事实。
3. HR10 先盘点旧 employee/profile/documents/workflow/notification 的可复用技术，再建立计划→项目→申请→参与→过程→评价→成果→核验→档案事实链。
4. 培训证书不自动等于法定资格；企业实践天数不自动等于质量；自报数据不自动标记 VERIFIED。
5. 两模块正式注册、MySQL gate、租户/权限/审计与迁移对账通过前，不标记 READY，不删除 legacy 基线。

## 4. 当前已落地骨架

`hr_qualification/` 与 `hr10_development/` 已有 README、`module_contract.py` 和合同测试；模块合同已明确 HR09 不直接写 HR03/HR10/HR12，HR10 以已核验发展事实向 HR09/HR12 输出。

## 5. 下一块代码

优先为 HR09 落 **qualification/document legacy evidence adapter + 证据类型分层测试**；HR10 随后落 **Development Plan / Program 最小权威链路**，所有旧 workflow/notification 仅通过 adapter 接入。
