# 0. 结论先行

HR06 是整个人事系统防止“今天改了一个字段，过去全变了”的核心交易域。

完整业务链必须是：

```text
选择人员 / 发起异动
        ↓
选择 ChangeAction + ChangeReason
        ↓
读取 effective-date 前一刻权威事实
        ↓
填写 Proposed Changes
        ↓
规则校验 / 岗位编制校验 / 冲突校验
        ↓
影响分析 Preview
        ↓
审批
        ↓
APPROVED_WAITING_EFFECTIVE
        ↓ 到达 effective_at
生效事务
        ├─ 关闭旧 effective-dated fact
        ├─ 写入新 fact
        ├─ HR02 岗位占用/释放/预占
        ├─ HR03 Assignment/Employment 更新
        ├─ 生成 Change Snapshot
        ├─ Outbox
        └─ Legacy WorkInformation Projection
        ↓
下游对账 / 通知 / 必要协同任务
```

HR06 必须回答：

1. 发生了什么类型的人事变化？
2. 为什么变化？
3. 变化前是什么？
4. 变化后是什么？
5. 哪一天开始有效？
6. 谁提出、谁批准？
7. 影响哪些组织、岗位、薪酬、权限、考勤、教务等下游？
8. 是否允许撤回、撤销、更正、回退？
9. 如果是临时异动，何时自动/人工返岗？
10. 如果未来又发生另一项异动，两个 future-dated event 如何排序和冲突？

禁止低质量实现：

- 直接 `EmployeeWorkInformation.department_id = new_department`；
- 直接改 `job_position_id`；
- 直接改 `employee_type_id`；
- 直接改 `reporting_manager_id`；
- 一个“编辑员工”表单完成所有异动；
- 没有 effective date；
- 没有 event reason；
- 没有 before/after；
- 批准即立刻覆盖，即使生效日在未来；
- future-dated 变更互相覆盖；
- 回退异动靠手工把字段改回去；
- 借调结束把人“再改一次部门”但没有 return relation；
- 兼岗直接覆盖主岗；
- 转岗和职称聘任混成一回事；
- 组织调动和薪酬变化绑死成一个不可拆动作；
- 岗位无空缺也能调入；
- 人已离职/待离职仍可生效未来调动；
- 人员异动审批后 HR02 岗位仍未占用；
- 旧岗位未释放；
- 变更后 HR03 和 Horilla WorkInformation 数据不一致；
- 通过 Excel 直接更新当前字段绕过 Change Service；
- 普通学院 HR 能把人调到其他学院而无目标单位授权；
- 调动时看到目标岗位就代表有权写；
- 用 `is_active` 代表异动状态；
- 用 simple-history 代替业务异动台账；
- 把“数据纠错”与“业务异动”混为一谈；
- 删除正式异动记录；
- 已生效事件任意 edit；
- downstream 同步失败就回滚已经真实生效的人事事实；
- 自动 fallback 到 legacy current state；
- 没有批量异动的原子性/部分失败策略。

# 2. 三家成熟 HCM 对标：共同精华

## 2.1 Workday：Change Job 是业务流程，不是改字段

Workday 的 Change Job / Move Workers 体现几个重要原则：

- Job Change 是正式 Business Process；
- 可以做 transfer、promote、change job；
- 变更和组织、position、security、benefits 等下游有联动；
- 支持 future effective date；
- 批量组织迁移也仍逐 worker 形成变更处理；
- 正式业务流程可 rescind；
- 移动 worker/position 时有 staffing model 约束。

跃科吸收：

```text
PersonnelChangeCase
→ Approval
→ Future Effective
→ Apply
→ Rescind/Correct
```

不做“直接保存”。

## 2.2 SAP SuccessFactors：Event + Event Reason + Effective-dated Job Information

SAP Employee Central 把：

```text
Transfer
Promotion
Demotion
Job Change
Assignment
Data Change
Return to Work
Global Assignment
...
```

定义为 Event，并要求 Event Reason。

Event Reason 还可以控制：

- employee status；
- position follow-up；
- payroll event；
- 是否出现在 internal job history；
- future record 行为。

Job Information 变更按 effective date 形成新的历史记录。

跃科吸收：

```text
ChangeAction
ChangeReason
EffectiveDate
Rule/FollowUp Policy
History
```

## 2.3 Oracle HCM：Action/Reason + Work Relationship + Assignment 分层

Oracle 对 Transfer、Change Assignment、Promote、Add Assignment、Temporary Assignment 分层。

关键思路：

- Transfer 可以只更新 Assignment，不改变 Work Relationship；
- Add Assignment 创建额外 Assignment，主 Assignment 保留；
- Temporary Assignment 有 source assignment 和 return；
- Action + Reason 描述原因；
- Assignment 采用 date-effective update；
- Correction 与 Update 是不同语义；
- assignment-level security。

跃科吸收：

> **永久调动、增加兼岗、临时借调、纠错，必须是不同命令。**

# 3. 中国高校业务校正

高校常见人事异动至少包括：

```text
校内调动
转岗
岗位等级变化（注意 HR14 聘任边界）
行政职务变化
人员类别变化
用工性质变化
主岗/兼岗
借调
挂职
返岗
部门撤并引起批量迁移
```

高校公开制度中，常见明确区分：

- 校内调动：不同单位、同类别岗位间调整；
- 校内转岗：不同岗位类别之间调整，例如管理、专业技术、工勤技能岗位之间。

因此系统不能只有一个 `TRANSFER`。

- PostCatalog；

```text

→ 验证容量
→ 预占
→ 生效时提交/释放
```

## 4.2 HR03

HR03 权威：

```text
StaffMaster
EmploymentRelationship
Assignment
```

HR06 负责“请求改变”，HR03 Service 负责“按有效日期写事实”。

## 4.3 HR07

合同变更是 HR07 权威。

若异动导致合同条款变化：

```text
HR06 emits ContractReviewRequired
```

而不是 HR06 自建合同。

## 4.4 HR14

岗位聘任/职级晋升是 HR14 权威。

HR06 可以处理：

```text
从学院A教师岗 → 学院B教师岗
```

但正式专业技术岗位等级聘任、竞聘结果属于 HR14。

## 4.5 HR15

薪酬变化属于 HR15 权威。

HR06 发：

```text
CompensationRecalculationRequested
```

## 4.6 HR11

考勤规则可能随组织/岗位/人员类别变化。

HR06 发：

```text
AttendanceRuleReevaluationRequested
```

## 4.7 数字校园/教务

教师所属单位、教学身份当前投影可能变化，但历史课程/成绩/审批事实不得重写。

# 10. Case 状态机

```text
DRAFT
→ VALIDATING
→ READY_TO_SUBMIT
→ SUBMITTED
→ UNDER_APPROVAL
→ RETURNED
→ RESUBMITTED
→ APPROVED_WAITING_EFFECTIVE
→ APPLYING
→ EFFECTIVE
→ CLOSED
```

终止：

```text
REJECTED
WITHDRAWN
CANCELLED
APPLY_FAILED
RESCINDED
CORRECTED
```

必须区分：

- RETURNED：可补充重新提交；
- REJECTED：审批终局；
- WITHDRAWN：发起人主动撤回；
- CANCELLED：管理员依法取消未生效案件；
- RESCINDED：已生效后执行正式撤销；
- CORRECTED：业务事件成立，但某些数据被正式纠正。

# 11. Future-dated Event

这是 HR06 的 P0。

批准日可能：

```text
2026-08-08
```

生效日：

```text
2026-09-01
```

批准后不得提前改 Current Assignment。

状态：

```text
APPROVED_WAITING_EFFECTIVE
```

后台 Scheduler/Job：

```text
find due cases
→ lock
→ revalidate
→ apply
```

同时允许管理员有权限执行“立即提前生效”，但必须新 reason 和审计。

# 12. 同一人员 Future Event 冲突

例如：

```text
9月1日 调学院
10月1日 转岗位类别
```

可以共存。

但：

```text
9月1日 调A学院
9月15日 调B学院
```

必须检测依赖和链式基础。

每个 case 保存：

```text
base_snapshot_version
base_effective_at
```

审批/生效前重新 rebase。

结果：

```text
NO_CONFLICT
REBASE_REQUIRED
HARD_CONFLICT
```

禁止静默用旧快照生效。

# 21. HR06-02 校内调动施工卡

## 21.1 定义

校内调动：

> 同一学校内，人员主组织或主岗位发生永久性迁移，通常保留当前 EmploymentRelationship。

典型：

```text
学院A → 学院B
部门A岗位P1 → 部门B岗位P2
```

## 21.2 页面

```text
/hr/changes/transfers
/hr/changes/transfers/new
/hr/changes/transfers/:id
```

核心页面：

```text
┌──────────────────────┬──────────────────────┐
│ 当前任职              │ 拟调任               │
│ 计算机学院            │ 人工智能学院          │
│ 软件工程教师 P001     │ AI教师 P088          │
│ 主岗                  │ 主岗                 │
│ 1.0 FTE               │ 1.0 FTE              │
├──────────────────────┴──────────────────────┤
│ 生效：2026-09-01  原因：工作需要             │
├─────────────────────────────────────────────┤
│ 岗位容量 ✓  组织有效 ✓  Future conflict ✓    │
│ 当前课程：有（历史不回写）                    │
│ 考勤规则：将变化                               │
│ 工资：需重新评估                               │
└─────────────────────────────────────────────┘
```

## 21.3 Apply

永久调动：

```text
旧 primary assignment:
effective_to = effective_at - precision

新 primary assignment:
effective_from = effective_at
```

实现上按 HR03 effective-dated 规则，不使用“日期减一天”这种硬编码；统一采用 `[effective_from, effective_to)` half-open interval。

推荐：

```text
[start, end)
```

例如旧：

```text
[2024-09-01, 2026-09-01)
```

新：

```text
[2026-09-01, ∞)
```

避免日期边界错误。

## 21.4 Position

目标 position：

```text
reserve before approval/final approval
commit at effective date
```

旧 position：

```text
release at effective date
```

必须同一业务事务/可补偿 saga。

# 23. 调动和历史教务事实

禁止：

```text
2026 调学院
→ 2025 成绩单教师学院也变成新学院
```

数字校园对历史事实使用历史快照/as-of。

```text

```

下游当前目录更新，不回写历史记录。

# 28. Return

返岗不是手工编辑。

生成：

```text
RETURN_FROM_TEMPORARY
```

Return Service：

- 关闭 temporary assignment；
- 恢复/调整 source assignment；
- 检查原岗位仍有效；
- 若原岗位已撤销，进入 exception flow；
- 恢复当前投影；
- downstream events。

# 34. Correction vs Change

非常重要。

## Change

业务现实发生变化：

```text
2026-09-01 张三从A学院调到B学院
```

## Correction

发现原记录录错：

```text
实际是9月1日，但系统误录成9月2日
```

Correction 不应伪造成第二次“调动”。

# 36. Rescind

Rescind = 正式撤销已生效业务事件。

不是删除。

流程：

```text
EFFECTIVE
→ RESCIND_REQUESTED
→ RESCIND_APPROVED
→ RESCIND_APPLYING
→ RESCINDED
```

必须：

- 检查后续依赖事件；
- 若后续事实建立在此异动上，可能禁止直接 rescind；
- 要求 chain rollback/rebase。

---

# 37. 后续依赖检查

案例：

```text
9月1日 A→B
10月1日 B→C
```

想撤销 9月1日：

不能简单回 A。

因为 10月1日依赖 B。

结果：

```text
DEPENDENT_CHANGES_EXIST
```

必须人工处理。

# 48. 生效事务

伪代码：

```text
apply_change(case):
    lock(case)
    ensure APPROVED_WAITING_EFFECTIVE
    ensure due
    revalidate current facts
    rebase if needed
    lock required HR02 positions
    call HR03 domain service
    update HR02 occupancy/reservation
    save effective snapshot
    save transition
    create outbox
    mark EFFECTIVE
```

外部系统不在 DB transaction 内同步等待。

# 63. DB Constraints

至少：

- case_no tenant unique；
- action/reason compatible；
- effective_at not null after submit；
- one current effective snapshot per case；
- temporary link one active per source/change semantics；
- version >= 1；
- tenant FK一致；
- primary assignment invariant 在 HR03 service 保障并尽可能 DB constraint；

# 84. 参考依据

成熟产品设计思想：

- Workday Change Job / Move Workers：正式 Business Process、effective date、security、downstream impact、rescind；
- SAP SuccessFactors Employee Central：Event + Event Reason、Promotion/Demotion、Change Job、effective-dated Job Information、history；
- Oracle Fusion Cloud HCM：Action/Reason、Transfer、Change Assignment、Add Assignment、Temporary Assignment、effective-dated Assignment、assignment-level security。

中国高校制度校正：

- 高校校内调动与转岗管理中，通常明确区分“同类岗位间校内调动”与“不同岗位类别之间转岗”；
- 实际审批、岗位容量、组织接受、档案留痕均应参数化适配学校制度；
- 不将某一学校的审批级数、具体天数、岗位政策写死为全国统一逻辑。
